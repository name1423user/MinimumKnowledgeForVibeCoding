# break-it — 壊し方をテストに変換する

対応章: [第5章 壊す](../../chapters/05-breaking-it.md)

役割: パイプラインの**「テスト」**段階であり、**分岐点**。`happy-path-audit`と`security-baseline`が出した優先リストを受け取り、そこを最優先でテスト化する。結果は3種類に分類し、「想定外のバグ」は`notice-it`へ、「仕様不明」は`spec-first`へ送り返す。

## 目的

「動く」ことの確認だけでは不十分（[1.3節](../../chapters/01-ai-writes-code.md#13-動くと正しいは違う)）。実際に壊してみて見つけた問題を、二度と同じ理由で壊れないようテストコードに変換する（[5.2節](../../chapters/05-breaking-it.md#52-壊し方をテストコードに変換する)）。

## 使うタイミング

- 実装が一通り終わり、テストを書く/追加する段階
- 既存のテストが十分か疑わしい時
- `happy-path-audit`や`security-baseline`で「未対応」と判定された項目をテスト化する時

## 入力（前段から受け取るもの）

- `happy-path-audit`の「未対応」リスト（優先度つき）
- `security-baseline`の「認可漏れ」「前提条件が崩れている」リスト → 権限不足テストとして追加
- どちらもない場合は、[5.1節](../../chapters/05-breaking-it.md#51-壊し方の観点)の3系統をゼロから洗い出す

## 手順

「どう壊すか」を3系統に分けて考えると、抽象的な観点より具体的なテストケースに落とし込みやすい。

### 1. 入力を壊す

空文字・巨大値・不正な型・境界値（0、負数、最大値）を渡す。

### 2. 状態を壊す（特に「途中で壊れる」ケースを重視する）

- **二重実行**: 同じ処理が同時に2回走る
- **データ破損**: 保存されているデータの形式が壊れている
- **途中終了**: 処理の途中でプロセスが再起動する、例外が飛ぶ。「一部だけ保存された」「一部だけ送信された」のような中途半端な状態が残らないかを重点的に確認する

### 3. 外部環境を壊す

- **ネットワーク切断**: 通信の途中で相手が応答しなくなる
- **APIタイムアウト**: 外部APIが極端に遅い、またはエラーを返す

### 4. 権限を壊す

`security-baseline`から権限不足・認可漏れの指摘がある場合、「本来アクセスできないユーザーが呼んだらどうなるか」をテストに追加する。

### 5. テストとして書く

既存テストでカバーされていない項目のうち、対象コードに実際に関係するものを選び、プロジェクトで使われているテストフレームワークでテストを書く。

### 6. 壊した結果を3種類に分類する

テストを実行した結果は、必ず次の3種類に分けて記録する。この分類こそが`break-it`の一番の役割で、3番目が特に重要。

- **期待通り拒否された**: バリデーションやエラー処理が意図した通りに機能した（問題なし）
- **想定外に壊れた**: 明確なバグ。例: 存在しないIDを渡すと500エラーになる（本来404であるべき）→ 修正が必要な項目として`notice-it`（本番でどう気づくか）に引き渡す
- **挙動が不明確だった**: バグか仕様か判断できない。例: APIタイムアウト時に何も表示されず処理が終わる（エラーを出すべきか、リトライすべきか、仕様が決まっていない）→ **`spec-first`に差し戻す**。ここでコードを直すのではなく、質問形式に変換して仕様を確定させる

## 出力フォーマット

```
## 壊し方チェック: <対象コード名>

凡例: 分類は「期待通り拒否された（問題なし）」「想定外に壊れた（バグ、修正が必要）」「挙動が不明確だった（仕様が決まっていないので、実装より先に仕様を決める）」の3種類。

### 優先対応（happy-path-audit / security-baseline から引き渡し）
1. rate負数の境界値
   \`\`\`python
   def test_discount_negative_rate_raises():
       with pytest.raises(ValueError):
           calculate_discount(price=1000, rate=-10)
   \`\`\`
2. 権限のないユーザーによる削除（security-baselineの認可漏れ指摘より）

### 結果の分類
| ケース | 分類 | 詳細 |
|---|---|---|
| rate負数 | 想定外に壊れた | 500になる。修正が必要 |
| 存在しないID | 期待通り拒否された | 404が返る。対応済み |
| APIタイムアウト30秒無応答 | 挙動が不明確 | エラー表示すべきかリトライすべきか仕様が無い |

### 状態を壊す（途中終了ケースを含む）
- 決済処理の途中でプロセスが落ちた場合、二重課金にならないか → 未確認、要調査

## 次にすること
「想定外に壊れた」の行から先に直す。「挙動が不明確」の行はコードをいきなり直さず、書かれている質問に自分で答えるか、`spec-first`で仕様を先に決めてから対応する。
```

## 出力（次段への引き渡し）

- **想定外に壊れた**項目 → `notice-it`へ「本番で気づける必要がある失敗パターン」として引き渡す
- **挙動が不明確だった**項目 → `spec-first`へ差し戻す。質問形式に変換して渡す（例: 「APIタイムアウト時、エラー表示・リトライ・無反応のどれを仕様としますか？」）
- 差し戻しが発生した場合、それ以降の`notice-it`・`ci-readiness`は該当項目の仕様確定待ちとして保留する（[停止条件](../vibe-coding-checklist/SKILL.md#停止条件critical)には満たない限りは、他の項目は先に進めてよい）

## やらないこと

- 見つかった不具合を無断で修正しない。テストとして再現し、修正はユーザーの指示を待つか、別途相談する
- 対象と無関係な観点までテストを量産しない。コードの実際の使われ方に関係する系統に絞る

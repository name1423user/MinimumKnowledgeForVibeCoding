# spec-first — 実装前の仕様レビュー

対応章: [第3章 設計する](../../chapters/03-design.md) / [第4章 AIを監督する](../../chapters/04-supervising-ai.md)

役割: パイプラインの**「作る前」**段階であり、かつ**ループの合流点**。ここで固めた受け入れ条件が、後段の`happy-path-audit`と`break-it`の判定基準になる。仕様変更や「仕様不明」の差し戻しは、すべてここに戻ってくる。

## 目的

「動くもの」を素早く作る前に、**何を作るべきか**と**何を満たせば完成なのか**を言葉にできているかを確認する。ここを飛ばすと、[1.4節](../../chapters/01-ai-writes-code.md#14-aiがハッピーケースしか考えない理由)の「ハッピーケースだけの実装」が量産され、後段のチェックにも判定基準が渡らない。

## 使うタイミング

- ユーザーから機能追加・修正の依頼を受け、すぐ実装に取りかかろうとしている時
- 依頼文が「〜な感じで」「〜っぽく」のように曖昧な時
- 実装前に一度、依頼内容を要約して確認したい時

## 手順

1. **要件を1文で書く**: 「何を実現したいか」だけを抜き出す（[3.1節](../../chapters/03-design.md#31-要件と仕様)）
2. **仕様を書き出す**: 「それをどう振る舞いとして定義するか」を、正常系・異常系・権限の観点でリスト化する
3. **受け入れ条件に変換する**: 仕様を「〜すれば完成」というテスト可能な形に落とす。ここが後段のチェックの判定基準になるので省略しない
   - 例: 要件「ノートを削除できる」→ 仕様「削除確認後にDBから削除する」→ 受け入れ条件「削除後に一覧から消える／存在しないIDでは404を返す」
4. **曖昧な点を質問形式に変換する**: 「要確認」と書いて終わらせず、ユーザーが即答できる質問にする
   - 悪い例: 「削除済みIDの場合 → 要確認」
   - 良い例: 「削除済みIDを再度指定した場合、404にしますか、それとも成功扱い（既に削除済み）にしますか？」
5. **曖昧な依頼文自体も精度の高い表現に変換する**（[4.1節](../../chapters/04-supervising-ai.md#41-良いプロンプトの作り方)の表と同じ形式でbefore/afterを提示）
6. **仕様メモとして提示し、実装前にユーザーの確認を取る**

## 出力フォーマット

```
## 仕様メモ

**要件**: <1文>

**仕様**
- 正常系: ...
- 異常系: ...
- 権限: ...（関係ない場合は省略可）

**受け入れ条件**（後段のチェックがこれを判定基準に使う）
- [ ] 削除後、一覧から消えている
- [ ] 存在しないIDを渡すと404が返る

**確認したいこと**（要確認事項を質問化）
- Q1: 削除済みIDを再度指定した場合、404か成功扱いか？

**この理解で実装を進めてよいですか？**

## 次にすること
「確認したいこと」の質問にすべて答えてから実装を始める。曖昧なまま進めると、後段の`happy-path-audit`・`break-it`が何を基準に判定すればいいか分からなくなり、チェック自体が機能しなくなる。
```

## 入力（後段から戻ってくるもの）

このskillはパイプラインの起点だが、次のきっかけで**再実行される**（ループの合流点）。

- ユーザーから仕様変更の発言があった時（「やっぱり削除じゃなくアーカイブにして」等）
- `break-it`から「挙動が不明確（バグか仕様か判断できない）」という差し戻しがあった時
- いずれかのskillが[停止条件（CRITICAL）](../vibe-coding-checklist/SKILL.md#停止条件critical)を検出し、パイプラインが停止して戻ってきた時

## 仕様変更時の再レビュー

実装が始まった後に仕様変更が発生した場合、次を必ず行う。

1. 変更後の要件・仕様・受け入れ条件を再確定する
2. **旧受け入れ条件との差分を明示する**（何が変わったか、何が無くなったか）
3. 旧仕様に基づいて書かれた実装・テストが残っていないか一覧化する。残っている場合は「削除/更新対象」として`happy-path-audit`・`break-it`に引き渡す
4. `break-it`から「挙動が不明確」で差し戻された項目は、質問4と同じ形式（質問に変換する）でユーザーに確認する

これを省略すると、古い受け入れ条件を使ったチェックが後段に残り続け、パイプライン全体の判定基準がずれる。

## 出力（次段への引き渡し）

- `受け入れ条件`リストを、`happy-path-audit`と`break-it`が判定基準として使う。実装後のレビューは「この受け入れ条件を満たしているか」を軸に行う
- 仕様変更・差し戻しで再実行した場合は、「更新後の受け入れ条件」と「無効になった旧項目」を分けて渡す

## やらないこと

- 質問への回答をこのskillが勝手に決めない。ユーザーの回答を待ってから仕様を確定する
- 受け入れ条件が確定していない項目は、後段に「未確定」として渡す（推測で埋めない）

# notice-it — 観測可能性チェック

対応章: [第2章 コードを読むための最低限の知識](../../chapters/02-reading-code.md) / [第3章 設計する](../../chapters/03-design.md) / [第6章 気づく](../../chapters/06-noticing.md)

役割: パイプラインの**「本番」**段階。`break-it`で見つかった「途中で壊れるケース」が、実際に本番で気づける状態になっているかを確認する。

## 目的

意図的に壊す（[第5章](../../chapters/05-breaking-it.md)）とは対になる、「本番で勝手に壊れた時にどう気づくか」を確認する。一番怖いのは、エラーが起きたことにすら誰も気づかない状態（[6.3節](../../chapters/06-noticing.md#63-壊れたが誰も気づかなかったを防ぐ)）。**ログが存在すること自体は「気づける」ことの証明にならない**。誰も見ていないログは、ログが無いのと結果的に同じになる。

## 使うタイミング

- コードレビュー時、エラー処理・ログの妥当性を確認したい時
- 「なぜかこのバグに誰も気づかなかった」という事後調査の時
- 責務が混在した関数を見つけたい時
- `break-it`で「途中終了」「外部環境の失敗」ケースが見つかった直後

## 入力（前段から受け取るもの）

- `break-it`で見つかった「本番で起きうる失敗パターン」（途中終了、外部環境の失敗など） → これらが観測可能性のパイプラインに乗っているかを重点的に確認する

## 手順

「ログ→検知→通知→調査」の4段階が繋がっているかを確認する。1段階だけ整っていても、次の段階が繋がっていなければ気づけない。

1. **ログ**（[6.1節](../../chapters/06-noticing.md#61-ログ設計)）: 失敗しうる処理（外部API呼び出し・DB操作・決済など）で、失敗時に「何が」「いつ」「どんな入力で」を記録しているか。`except: pass`のように例外を握りつぶして何も記録していない箇所を探す（[2.4節](../../chapters/02-reading-code.md#24-エラー処理)）。ログを追加・強化する際は、パスワード・APIキー・トークンなどをそのまま出力していないか（`security-baseline`の秘密情報チェックと合わせて確認する）
2. **検知**: エラーログは記録されるだけで終わっていないか。失敗件数やエラー率をメトリクスとして把握できる仕組み（カウンタ、集計）があるか
3. **通知（「正常に失敗する」を区別する）**: すべての失敗を通知すると、アラート疲れで本当に重要な通知が埋もれる。「記録すべき失敗」と「人間を起こすべき失敗」を分けて設計されているかを確認する

   | 事象の例 | 対応 |
   |---|---|
   | ユーザーがパスワードを1回間違えた | ログのみ（想定内の失敗。ただし連続失敗は別途検知対象） |
   | APIタイムアウトが単発で1件 | ログのみ |
   | DB接続断が5分間続いている | 通知（アラート） |
   | APIエラー率が閾値（例: 30%）を超えた | 通知（アラート） |

   単発の失敗を1件ごとに通知していないか、逆に本来アラートすべき「継続する失敗」「高いエラー率」が閾値なしで埋もれていないかを確認する
4. **調査**: 通知を受けた後、原因調査に必要な情報（入力値、ユーザーID、スタックトレース）がログに紐づいているか。「エラーが起きたことは分かるが、なぜかは分からない」状態になっていないか
5. **リトライの暴走がないか**: 失敗した処理が無限にリトライされ続け、ログだけが埋まっていく状態（サイレントな異常）になっていないか

追加で、責務の混在（[3.4節](../../chapters/03-design.md#34-責務分離)）も確認する: 1つの関数の説明に「〜して、〜して」と「て」が2回以上出てくる関数を探す。

## 出力フォーマット

```
## 観測可能性チェック: <対象コード名>

凡例: 状態は「対応済み（このままでよい）」「部分対応（一部足りない）」「未対応（何も無い）」の3種類。段階は上から順につながって初めて「気づける」状態になる。

| 段階 | 状態 | 詳細 |
|---|---|---|
| ログ | 未対応 | process_payment()のexcept節で何も記録せずreturnしている（重大） |
| 検知 | 部分対応 | ログはあるが失敗件数を集計する仕組みがない |
| 通知 | 未対応 | 決済失敗時にアラートが飛ぶ経路がない |
| 調査 | 対応済み | user_id/amountはログに含まれている |

### break-itからの引き渡し項目への対応
- 「決済処理の途中終了」→ ログ・検知・通知のいずれも未対応。最優先で対応を推奨

### 責務の混在
- register_user(): 検証・保存・通知の3責務が1関数に混在

## 次にすること
「未対応」の段階から順に埋める。特に「ログ」が未対応だと、後の「検知」「通知」「調査」を整えても意味がないので最優先で対応する。
```

## やらないこと

- ログの追加・通知経路の構築・関数の分割を無断で行わない。指摘と改善案の提示までに留め、実施はユーザーの判断を待つ

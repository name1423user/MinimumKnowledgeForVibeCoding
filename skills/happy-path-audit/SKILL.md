# happy-path-audit — ハッピーケース検出

対応章: [第1章 AIにコードを書かせる](../../chapters/01-ai-writes-code.md) / [第5章 壊す](../../chapters/05-breaking-it.md)

役割: パイプラインの**「作った直後」**段階。`spec-first`の受け入れ条件を判定基準に使い、見つけた未対応項目を`break-it`に優先テスト化として引き渡す。

## 目的

AIは典型的な入力を前提にした実装をしがちで、非典型ケースは明示的に頼まない限り出てこない（[1.4節](../../chapters/01-ai-writes-code.md#14-aiがハッピーケースしか考えない理由)）。実装が「動く」ことと「正しい」ことは別物（[1.3節](../../chapters/01-ai-writes-code.md#13-動くと正しいは違う)）という前提で、対象コードを読み直す。

## 使うタイミング

- AIに実装させた直後、そのままコミット・PRに進む前
- 「このコード大丈夫？」と聞かれた時
- 既存コードの弱点を把握したい時

## 手順

### 0. 観点を選別する（形式的なレビューにしないための工程）

[5.1節](../../chapters/05-breaking-it.md#51-壊し方の観点)の観点を機械的に全部当てはめず、まず対象コードの性質を見て**関係する観点だけ**を選ぶ。

- 外部からの入力を受け取るか？ → 境界値・異常系・空データ・巨大データが関係する
- 状態（DB・ファイル・グローバル変数）を変更するか？ → 同時実行・二重実行・データ破損が関係する
- 外部システム（ネットワーク・API）を呼ぶか？ → ネットワーク切断が関係する
- 呼び出し元の権限によって振る舞いが変わるか？ → 権限不足が関係する

純粋な文字列変換関数のような、入出力が値だけで完結する処理には「ネットワーク切断」のような観点は当てはめない。**関係しない観点は「対象外（理由）」として明示し、無理に埋めない。**

### 1. 選別した観点で判定する

| 観点 | 確認する質問 |
|---|---|
| 境界値 | 0、負数、最大値、配列の先頭/末尾を渡したらどうなるか |
| 異常系 | 型が違う値、必須項目の欠落を渡したらどうなるか |
| 空データ | 空文字列・空リスト・存在しないIDを渡したらどうなるか |
| 巨大データ | 想定より桁違いに大きい入力・ファイルを渡したらどうなるか |
| 同時実行 | 同じ処理が同時に2回走ったらどうなるか |
| ネットワーク切断 | 外部呼び出しの途中で相手が応答しなくなったらどうなるか |
| 権限不足 | 権限のないユーザーが呼んだらどうなるか |
| 二重実行 | 同じ操作（決済・送信など）が2回実行されたらどうなるか |

各項目を「対応済み」「未対応」「対象外（理由）」の3値で判定する。

### 2. 受け入れ条件との照合（`spec-first`の結果がある場合）

`spec-first`が受け入れ条件を出している場合、それも満たしているか併せて確認する。

### 3. 過剰実装チェック（頼んでいないことをしていないか）

「実装されていないもの」の逆に、**頼んでいないのに実装されているもの**も見る。AIは親切心や「典型的な実装」の学習傾向から、受け入れ条件にない振る舞いを勝手に追加することがある。

- 削除機能なのに、頼んでいない自動バックアップまで追加している
- APIエラー時に、頼んでいない自動リトライを実装している
- 未定義のパラメータに、頼んでいないデフォルト値を勝手に設定している
- 権限不足時に、エラーにせず別のユーザー・別のコンテキストとして処理を続行している

受け入れ条件（`spec-first`の出力）に無い振る舞いを見つけたら、「バグではないが未依頼の動作」として別枠で報告する。これも意図しない副作用の温床になりうるため、`happy-path-audit`が最も見つけやすい。

## 出力フォーマット

```
## ハッピーケース診断: <対象コード名>

凡例: 判定は「対応済み（このままでよい）」「未対応（直したほうがよい）」「対象外（このコードには関係ないため外した）」の3種類。優先度は「高」から順に着手する目安。

対象外にした観点: ネットワーク切断（外部呼び出しを含まないため）

| 観点 | 判定 | 根拠・懸念点 | 優先度 |
|---|---|---|---|
| 境界値 | 未対応 | rate=-10 で割引額が負になる | 高 |
| 異常系 | 対応済み | 型チェックが入っている | - |

## 受け入れ条件との照合
- [ ] 存在しないIDでは404を返す → 未対応（500になる）

## 過剰実装（未依頼の動作）
- delete_note()が、頼んでいない「削除前に自動バックアップを保存」する処理を追加している → 意図か確認が必要

## break-itへの引き渡し（優先テスト化リスト）
1. rate負数の境界値（高）
2. 存在しないIDで404を返すべき点（受け入れ条件違反、高）
3. 過剰実装の自動バックアップが期待通りか（要確認）

## 次にすること
優先度「高」の項目から直すか、`break-it`に渡してテストにする。判定の理由に納得できない場合は、対応章（[第1章](../../chapters/01-ai-writes-code.md)・[第5章](../../chapters/05-breaking-it.md)）の該当節を読み返してから判断する。
```

## やらないこと

- 「未対応」と判定した箇所を無断で修正しない。対応案を提示し、ユーザーの判断を待つ
- 関係の薄い観点を無理にコードへ当てはめない。「対象外」と明記した上で理由を残す

# spec-first — 実装前の仕様レビュー

対応章: [第3章 設計する](../../../chapters/03-design.md) / [第4章 AIを監督する](../../../chapters/04-supervising-ai.md)

## 目的

「動くもの」を素早く作る前に、**何を作るべきかを言葉にできているか**を確認する。ここを飛ばすと、[1.4節](../../../chapters/01-ai-writes-code.md#14-aiがハッピーケースしか考えない理由)の「ハッピーケースだけの実装」が量産される。

## 使うタイミング

- ユーザーから機能追加・修正の依頼を受け、すぐ実装に取りかかろうとしている時
- 依頼文が「〜な感じで」「〜っぽく」のように曖昧な時
- 実装前に一度、依頼内容を要約して確認したい時

## 手順

1. **要件を1文で書く**: 「何を実現したいか」だけを抜き出す（[3.1節](../../../chapters/03-design.md#31-要件と仕様)）
2. **仕様を書き出す**: 「それをどう振る舞いとして定義するか」を、次の観点でリスト化する
   - 正常系: 何を入れたら何が起きるか
   - 異常系: 空・不正な形式・範囲外の値が来たらどうするか（[5.1節](../../../chapters/05-breaking-it.md#51-壊し方の観点)の観点を借りる）
   - 権限: 誰が実行できるか（[7.5節](../../../chapters/07-security.md#75-認証認可)）
3. **曖昧な表現を精度の高い表現に変換する**。[4.1節](../../../chapters/04-supervising-ai.md#41-良いプロンプトの作り方)の表と同じ形式で、before/afterを提示する
4. **仕様メモとして提示し、実装前にユーザーの確認を取る**。ユーザーが承認してから実装に進む

## 出力フォーマット

```
## 仕様メモ

**要件**: <1文>

**仕様**
- 正常系: ...
- 異常系: ...（未確定の場合は「要確認」と明記）
- 権限: ...（関係ない場合は省略可）

**この理解で実装を進めてよいですか？**
```

## やらないこと

- 仕様の最終決定をこのskillだけで下さない。異常系・権限などが不明な項目は「要確認」として残し、ユーザーに判断を仰ぐ（[1.2節](../../../chapters/01-ai-writes-code.md#12-aiに任せていい仕事ダメな仕事)の「危険」側の判断は人間に戻す）

# security-baseline — セキュリティの基本チェック

対応章: [第7章 セキュリティ](../../../chapters/07-security.md)

役割: パイプラインの**「攻撃者視点」**段階。見つけた認可漏れ・信頼境界の見落としを`break-it`に権限テストとして引き渡す。

## 目的

セキュリティの根っこは1つ: **外部から来たデータは、形式・内容ともに一切信用しない**（[第7章](../../../chapters/07-security.md)冒頭）。この原則が崩れている箇所を検出するが、パターンマッチだけでは「その攻撃が本当に成立するか」の前提を見落とす。**まず前提を確認してから**、脆弱性パターンを探す。

網羅的な脆弱性診断ではなく、AIが書いたコードに頻出する初歩的な穴を拾うためのチェックであることに注意する。

## 使うタイミング

- 外部入力（フォーム・URLパラメータ・APIレスポンスなど）を扱うコードを書いた/レビューする時
- 「セキュリティ大丈夫？」のような曖昧な依頼を受けた時（[4.1節](../../../chapters/04-supervising-ai.md#41-良いプロンプトの作り方)の表の変換先はこのskillが担う）
- Electron・デスクトップアプリのように「プロセス内部だから安全」と誤解しやすい構成を扱う時

## 手順

### 0. 前提確認（データの出所 → 信頼境界 → 使用箇所）

パターン検出の前に、対象の値について次を明らかにする。

- **出所**: この値は本当に外部入力か？（ユーザー入力、URLパラメータ、APIレスポンス、他プロセスからのメッセージ）
- **信頼境界**: どこを跨いでいるか？「同じアプリ内だから安全」という思い込みに注意する。例えばElectronアプリのRenderer（Webページ側）からMain（Node.js側）へIPCで渡るデータは、プロセスは同じでもRendererは外部サイトの読み込みやXSSの影響を受けうるため、**信頼境界を跨ぐ外部入力として扱う**
- **使用箇所**: この値はSQL・HTML・シェルコマンド・ファイルパスのどこに使われるか
- **既存の防御**: 「認証済みだから安全」と思い込んでいないか（認証と認可は別。[7.5節](../../../chapters/07-security.md#75-認証認可)）。DB側の制約（UNIQUE、外部キー、CHECK）がアプリ層の検証の代わりとして機能していないか（アプリ層のバリデーションが抜けていても気づかれない一因になる）

前提確認で「信頼境界を跨いでいない」「防御が別レイヤーで効いている」と判断した場合は、その根拠を明記した上で対象外にしてよい。

### 1. パターンを検出する

1. **SQL Injection**（[7.2節](../../../chapters/07-security.md#72-sql-injection)）: 文字列結合・f文字列でSQLを組み立てている箇所
2. **XSS**（[7.3節](../../../chapters/07-security.md#73-xssクロスサイトスクリプティング)）: 外部から来た値をエスケープせずHTMLに埋め込んでいる箇所。Electronでは`nodeIntegration`が有効なRendererに外部由来のHTML/スクリプトを流し込むと、ブラウザのXSS以上に影響が大きい（Node API access）ことに注意
3. **CSRF**（[7.4節](../../../chapters/07-security.md#74-csrfクロスサイトリクエストフォージェリ)）: 状態を変更するリクエストにCSRFトークンや同等の保護がないか
4. **認証・認可の漏れ**（[7.5節](../../../chapters/07-security.md#75-認証認可)）: ログインチェックのみで権限チェックがないエンドポイント、他人のリソースIDをそのまま受け取って処理している箇所
5. **秘密情報の漏洩経路**（[7.6節](../../../chapters/07-security.md#76-秘密情報)）: 直書きだけでなく、次の経路すべてを確認する
   - コード中にリテラルで存在する（直書き）
   - **ログ出力**にAPIキー・パスワード・トークンがそのまま出ている（例: `logger.error(f"failed: token={token}")`）。ログが機能していても、これ自体がセキュリティ事故になる
   - **APIレスポンス**に内部トークンやパスワードハッシュがそのまま含まれている
   - **エラーメッセージ**（ユーザーに表示される、または例外のスタックトレースに含まれる）に秘密情報が漏れている
6. **権限分離**（[7.7節](../../../chapters/07-security.md#77-権限分離)）: 1つの認証情報・プロセスに不必要に広い権限が与えられていないか

## 出力フォーマット

```
## セキュリティ基本チェック: <対象コード名>

### 前提確認
- IPC経由でRendererから受け取るnote.textは、Renderer側の脆弱性(XSS等)経由で汚染される可能性があるため、外部入力として扱う

| 種別 | 箇所 | 前提（出所→境界→使用箇所） | リスク | 対策案 |
|---|---|---|---|---|
| SQL Injection | search() 12行目 | URLパラメータ→HTTP境界→SQL文 | user_input を文字列結合でSQLに埋め込み | プレースホルダに変更 |
| 認可漏れ | delete_user() | ログイン済みユーザー→権限チェック無し→DELETE実行 | 他人のリソースを削除できる | 呼び出し元IDとリソース所有者の一致確認を追加 |
| 秘密情報のログ出力 | api_client.py 40行目 | 内部トークン→エラーログ→ログファイル | `logger.error(f"failed: token={token}")`でトークンが平文で残る | マスキング（`token=***`）してから出力 |

対象外にした項目: XSS（このエンドポイントはHTMLを返さずJSONのみのため）

## break-itへの引き渡し（権限テスト）
- delete_user(): 他人のuser_idを指定した場合に403になるかのテストを追加
```

## やらないこと

- ここでの「問題なし」は網羅的な保証ではない。本格的なセキュリティ診断が必要な場合は専門のセキュリティレビュー（`security-review`等）や第三者診断を案内する
- 修正を無断で適用しない。対策案の提示までに留める
- 前提確認を省略して「危険」と即断しない。信頼境界を跨いでいないと確認できた項目は対象外として明記する

# vibe-coding-checklist — 通しチェックリストの実行版（パイプライン）

対応章: [第10章 実践](../../../chapters/10-practice.md)

## 目的

[第10章](../../../chapters/10-practice.md)の「通しチェックリスト」を、個別skillを**並列の独立チェックではなく、前段の結果を次段が使うパイプライン**として実行する。各skillは「知識→実装させる→疑う→壊す→気づく」の1つの役割を担い、単体の精度より役割間の受け渡しが機能全体の質を決める。

## パイプラインの構造

```
spec-first        「作る前」  要件・仕様・受け入れ条件を確定
     │             （受け入れ条件を後段に渡す）
     ▼
   実装（このskillの範囲外）
     │
     ├──────────────┐
     ▼              ▼
happy-path-audit  security-baseline
「作った直後」      「攻撃者視点」
     │              │
     │  未対応リスト  │  認可漏れ・前提の見落とし
     └──────┬───────┘
            ▼
         break-it            「テスト」
     優先リストを最優先でテスト化
     （途中終了・外部環境の失敗ケースを特に重視）
            │
            │ 本番で起きうる失敗パターン
            ▼
         notice-it            「本番」
     ログ→検知→通知→調査が繋がっているか確認
            │
            ▼
       ci-readiness           「継続運用」
     上記すべてが自動で維持され続ける状態か確認
```

## 使うタイミング

- 実装が一段落し、PRを作成する前
- 機能をリリースする前の最終確認
- 「一通りチェックして」とだけ依頼された時

## 手順

1. **spec-first**を実行し、受け入れ条件を確定する（既に仕様が明確な場合はスキップしてよいが、その場合も受け入れ条件だけは明文化する）
2. **happy-path-audit**と**security-baseline**を実行する。両方とも「実装直後の静的な読み込み」段階なので、順序はどちらが先でも良いが、両方の出力（未対応リスト／認可漏れリスト）を次に持ち越す
3. **break-it**を実行する。手順2の2つの出力を**最優先のテスト対象**として扱い、そこから手を付ける。特に「途中で壊れる」ケース・権限テストを重視する
4. **notice-it**を実行する。break-itで見つかった「本番で起きうる失敗パターン」が、ログ→検知→通知→調査まで繋がっているかを確認する
5. **ci-readiness**を実行する。ここまでの対応がすべて自動で維持され続ける状態（CI・ブランチ保護・カバレッジ監視）になっているかを確認する
6. 各skillの出力を[第10章の通しチェックリスト](../../../chapters/10-practice.md#通しチェックリスト)のチェックボックスに対応させ、済/未のステータスでまとめる

## 出力フォーマット

```
## 通しチェックリスト結果: <対象機能名>

### パイプライン実行結果
1. spec-first: 受け入れ条件2件確定、未回答の質問1件あり
2. happy-path-audit / security-baseline: 未対応2件（rate負数、存在しないIDで500）、認可漏れ1件（delete_user、他人のリソースを削除可能）
3. break-it: 優先3件をテスト化。うち「途中終了」ケース(決済の二重課金)は未解決のまま検出
4. notice-it: 「決済の二重課金」はログ・検知・通知いずれも未対応 → 最優先の残課題
5. ci-readiness: CIはあるがマージゲートになっていない

### 総評
残課題の中で最も深刻なのは「決済処理の途中終了」系列（happy-path-audit → break-it → notice-itと3段にわたって指摘が連鎖している）。優先度: 決済の途中終了対応 > 認可漏れ修正 > CIのマージゲート化
```

## やらないこと

- 各skillの判定結果を上書き・簡略化しない。各skillの出力をそのまま集約する
- 「済」判定を推測で出さない。各skillを実際に実行した結果のみを反映する
- 手順2→3→4→5の順序を省略して並列に流さない。前段の出力が次段の優先順位を決めるという依存関係を崩さない

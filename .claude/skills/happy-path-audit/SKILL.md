# happy-path-audit — ハッピーケース検出

対応章: [第1章 AIにコードを書かせる](../../../chapters/01-ai-writes-code.md) / [第5章 壊す](../../../chapters/05-breaking-it.md)

## 目的

AIは典型的な入力を前提にした実装をしがちで、非典型ケースは明示的に頼まない限り出てこない（[1.4節](../../../chapters/01-ai-writes-code.md#14-aiがハッピーケースしか考えない理由)）。実装が「動く」ことと「正しい」ことは別物（[1.3節](../../../chapters/01-ai-writes-code.md#13-動くと正しいは違う)）という前提で、対象コードを読み直す。

## 使うタイミング

- AIに実装させた直後、そのままコミット・PRに進む前
- 「このコード大丈夫？」と聞かれた時
- 既存コードの弱点を把握したい時

## 手順

対象コード（関数・エンドポイント・差分）を読み、[5.1節](../../../chapters/05-breaking-it.md#51-壊し方の観点)の観点ごとに「考慮されているか」を確認する。

| 観点 | 確認する質問 |
|---|---|
| 境界値 | 0、負数、最大値、配列の先頭/末尾を渡したらどうなるか |
| 異常系 | 型が違う値、必須項目の欠落を渡したらどうなるか |
| 空データ | 空文字列・空リスト・存在しないIDを渡したらどうなるか |
| 巨大データ | 想定より桁違いに大きい入力・ファイルを渡したらどうなるか |
| 同時実行 | 同じ処理が同時に2回走ったらどうなるか |
| ネットワーク切断 | 外部呼び出しの途中で相手が応答しなくなったらどうなるか |
| 権限不足 | 権限のないユーザーが呼んだらどうなるか |
| 二重実行 | 同じ操作（決済・送信など）が2回実行されたらどうなるか |

各項目を「対応済み」「未対応」「対象外（理由）」の3値で判定する。

## 出力フォーマット

```
## ハッピーケース診断: <対象コード名>

| 観点 | 判定 | 根拠・懸念点 |
|---|---|---|
| 境界値 | 未対応 | rate=-10 で割引額が負になる |
| 異常系 | 対応済み | 型チェックが入っている |
...

## 未対応項目への対応案
- <具体的な修正提案 or 追加すべき確認事項>
```

## やらないこと

- 「未対応」と判定した箇所を無断で修正しない。対応案を提示し、ユーザーの判断を待つ
- 全観点を無理にコードへ当てはめない。「対象外」と明記した上で理由を残す

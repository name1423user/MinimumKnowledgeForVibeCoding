# break-it — 壊し方をテストに変換する

対応章: [第5章 壊す](../../../chapters/05-breaking-it.md)

役割: パイプラインの**「テスト」**段階。`happy-path-audit`と`security-baseline`が出した優先リストを受け取り、そこを最優先でテスト化する。

## 目的

「動く」ことの確認だけでは不十分（[1.3節](../../../chapters/01-ai-writes-code.md#13-動くと正しいは違う)）。実際に壊してみて見つけた問題を、二度と同じ理由で壊れないようテストコードに変換する（[5.11節](../../../chapters/05-breaking-it.md#511-壊し方をテストコードに変換する)）。

## 使うタイミング

- 実装が一通り終わり、テストを書く/追加する段階
- 既存のテストが十分か疑わしい時
- `happy-path-audit`や`security-baseline`で「未対応」と判定された項目をテスト化する時

## 入力（前段から受け取るもの）

- `happy-path-audit`の「未対応」リスト（優先度つき）
- `security-baseline`の「認可漏れ」「前提条件が崩れている」リスト → 権限不足テストとして追加
- どちらもない場合は、[5.1節](../../../chapters/05-breaking-it.md#51-壊し方の観点)の3系統をゼロから洗い出す

## 手順

「どう壊すか」を3系統に分けて考えると、抽象的な観点より具体的なテストケースに落とし込みやすい。

### 1. 入力を壊す

空文字・巨大値・不正な型・境界値（0、負数、最大値）を渡す。

### 2. 状態を壊す（特に「途中で壊れる」ケースを重視する）

- **二重実行**: 同じ処理が同時に2回走る
- **データ破損**: 保存されているデータの形式が壊れている
- **途中終了**: 処理の途中でプロセスが再起動する、例外が飛ぶ。「一部だけ保存された」「一部だけ送信された」のような中途半端な状態が残らないかを重点的に確認する

### 3. 外部環境を壊す

- **ネットワーク切断**: 通信の途中で相手が応答しなくなる
- **APIタイムアウト**: 外部APIが極端に遅い、またはエラーを返す

### 4. 権限を壊す

`security-baseline`から権限不足・認可漏れの指摘がある場合、「本来アクセスできないユーザーが呼んだらどうなるか」をテストに追加する。

### 5. テストとして書く

既存テストでカバーされていない項目のうち、対象コードに実際に関係するものを選び、プロジェクトで使われているテストフレームワークでテストを書く。

## 出力フォーマット

```
## 壊し方チェック: <対象コード名>

### 優先対応（happy-path-audit / security-baseline から引き渡し）
1. rate負数の境界値
   \`\`\`python
   def test_discount_negative_rate_raises():
       with pytest.raises(ValueError):
           calculate_discount(price=1000, rate=-10)
   \`\`\`
2. 権限のないユーザーによる削除（security-baselineの認可漏れ指摘より）

### 入力を壊す（追加分）
- ...

### 状態を壊す（途中終了ケースを含む）
- 決済処理の途中でプロセスが落ちた場合、二重課金にならないか → 未確認、要調査

### 外部環境を壊す
- ...

## notice-itへの引き渡し
- 「決済処理の途中終了」は本番で気づける必要がある → notice-itでログ・アラートの有無を確認
```

## やらないこと

- 見つかった不具合を無断で修正しない。テストとして再現し、修正はユーザーの指示を待つか、別途相談する
- 対象と無関係な観点までテストを量産しない。コードの実際の使われ方に関係する系統に絞る

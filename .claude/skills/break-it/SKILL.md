# break-it — 壊し方をテストに変換する

対応章: [第5章 壊す](../../../chapters/05-breaking-it.md)

## 目的

「動く」ことの確認だけでは不十分（[1.3節](../../../chapters/01-ai-writes-code.md#13-動くと正しいは違う)）。実際に壊してみて見つけた問題を、二度と同じ理由で壊れないようテストコードに変換する（[5.11節](../../../chapters/05-breaking-it.md#511-壊し方をテストコードに変換する)）。

## 使うタイミング

- 実装が一通り終わり、テストを書く/追加する段階
- 既存のテストが十分か疑わしい時
- `happy-path-audit`で「未対応」と判定された項目をテスト化する時

## 手順

1. 対象の関数・エンドポイントの入出力を確認する
2. [5.1節](../../../chapters/05-breaking-it.md#51-壊し方の観点)の10観点それぞれについて、既存テストでカバーされているか確認する
   - 境界値／異常系／空データ／巨大データ／同時実行／ネットワーク切断／権限不足／データ破損／再起動／二重実行
3. カバーされていない観点のうち、対象コードに実際に関係するものを選び、テストケースを書く（プロジェクトで使われているテストフレームワークに合わせる）
4. 「試したが問題なかった」項目と「試して問題が見つかった」項目を分けて報告する

## 出力フォーマット

```
## 壊し方チェック: <対象コード名>

### カバー済み
- 境界値: test_xxx_zero() で確認済み

### 未カバー（テスト追加を提案）
- 異常系: text キーが無い場合の挙動が未テスト
  \`\`\`python
  def test_missing_text_key_is_rejected():
      with pytest.raises(ValueError):
          validate_note({})
  \`\`\`

### 実際に壊してみて見つかった問題
- 同時実行: 2つのリクエストが同時に balance を更新すると不整合が起きる（要修正）
```

## やらないこと

- 見つかった不具合を無断で修正しない。テストとして再現し、修正はユーザーの指示を待つか、別途相談する
- 対象と無関係な観点までテストを量産しない。コードの実際の使われ方に関係する観点に絞る

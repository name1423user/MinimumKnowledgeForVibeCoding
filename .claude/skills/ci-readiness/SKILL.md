# ci-readiness — テストとCI/CDの信頼性チェック

対応章: [第8章 テストとCI/CD](../../../chapters/08-testing-and-cicd.md)

役割: パイプラインの**「継続運用」**段階。ここまでの`spec-first`〜`notice-it`の結果が、次回以降も自動で守られる状態になっているかを確認する最終ゲート。

## 目的

テストは「毎回、誰の手も借りずに、自動で」実行され続けて初めて価値を持つ（[第8章](../../../chapters/08-testing-and-cicd.md)冒頭）。**「CIが緑である」ことと「CIが信頼できる」ことは別物**。CI設定が存在するだけでは、テストが実質的に何も検証していない（vacuous pass）状態を防げない。

## 使うタイミング

- リリース・デプロイ前の確認
- CI設定を初めて導入する時、または見直す時
- 「テストが通ったのにバグが出た」といった事後調査

## 手順

### 1. 存在の確認

- CI設定ファイル（GitHub Actionsの`.github/workflows/`など）が存在するか
- Lint・型チェック・ビルドがCIの実行対象に含まれているか（テストだけに絞られていないか）

### 2. 信頼性の確認（ここが本質）

- **マージのゲートになっているか**: CIが失敗した状態でもマージできる設定になっていないか（ブランチ保護、必須チェックの設定）
- **テストが本当に実行されているか**: テストファイルはあるが実行対象から除外（`skip`, `xfail`, 実行対象パターンから漏れている）されていないか。アサーションが実質何も検証していない（`assert True`相当、モックが常に成功を返すだけ）テストがないか
- **カバレッジの急落を検知できるか**: カバレッジを計測しているか、計測していても閾値チェックがなく下がったまま気づかれない状態になっていないか
- **Flaky testの兆候**（[8.4節](../../../chapters/08-testing-and-cicd.md#84-cicdが壊れかけた時のサイン)）: CI設定にリトライ処理が入っている、実行順序やシステム時刻への依存が疑われるテストがないか

### 3. テストピラミッドの構成確認

単体テスト・結合テスト・E2Eテストのファイル数・実行時間のバランスを見て、極端な偏りがないか（[8.1節](../../../chapters/08-testing-and-cicd.md#81-テストピラミッド)）

### 4. デプロイ前チェックリストとの接続を確認する

CIが自動で確認できない項目（マイグレーション・機能フラグ・ロールバック手順、[8.5節](../../../chapters/08-testing-and-cicd.md#85-デプロイ前チェックリストとの接続)）を、人間が確認すべき項目として別途提示する

## 出力フォーマット

```
## CI/CD信頼性チェック

- CI設定: あり (.github/workflows/test.yml)
- マージゲート: なし → CI失敗でもマージ可能な状態（要修正、優先度高）
- Lint/型チェック: CIに含まれていない
- テストの実質性: test_notification.py が全件モック常時成功で、実質何も検証していない
- カバレッジ: 計測なし
- テストピラミッド: 単体42件 / 結合3件 / E2E0件 → 結合・E2Eが薄い
- Flaky testの兆候: test_send_email が3回リトライ設定 → 要調査
- CI対象外で人間が確認すべき項目: DBマイグレーションの有無、機能フラグの状態
```

## やらないこと

- CI設定ファイルの作成・変更を無断で行わない。現状の報告と改善案の提示までに留める

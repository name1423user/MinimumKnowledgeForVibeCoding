## 2.1 変数・関数・クラス

- **変数**: 値に名前をつけて保管する箱。「今どんな値が入っているか」を追えることが読解の基本
- **関数**: 処理のまとまりに名前をつけたもの。入力（引数）と出力（戻り値）の対応を意識する
- **クラス**: データとそれを操作する処理をひとまとめにした設計図。「このクラスは何を管理しているオブジェクトか」を一言で言えるかが理解の指標

## 2.2 型

値の種類（数値・文字列・真偽値・リストなど）。型が合わないと計算やAPIとのやり取りで想定外の挙動になる。「この変数は文字列のはずが数値だった」のようなズレが、バイブコーディングで頻発するバグの典型。

特に注意が必要なのが、JavaScriptやPythonのような動的型付け言語での**暗黙の型変換**だ。型が違っても言語側がエラーを出さず、勝手に「よしなに」変換してくれてしまう。

```javascript
// JavaScriptの暗黙の型変換
"5" + 3       // "53"  -- 文字列として連結される（+は文字列連結にもなる）
"5" - 3       // 2     -- こちらは数値として引き算される（-は数値専用）
"5" == 5      // true  -- 型変換した上で比較する「==」はこう判定する
"5" === 5     // false -- 型変換しない「===」ならfalseになる
```

APIから受け取った金額が文字列`"1000"`で届いているのに、それを検証せず他の数値と足し算すると、`"1000" + 500`が`"1000500"`という文字列になって金額計算が壊れる、といった事故が典型的に起きる。TypeScriptやmypyのような**静的型チェッカー**を導入すると、こうした型のズレを実行前（コンパイル・Lintの段階）で検出できる。AIに実装させる際も「型注釈をつけて」と一言添えるだけで、この種のバグが実行前に弾かれる可能性が上がる。

## 2.3 非同期処理

「今すぐ終わらない処理（通信、ファイル読み込みなど）」を、待っている間も他の処理を進められるようにする仕組み。`async`/`await`のような構文を見たら、「この処理は即座には終わらない」と意識する。待つべき箇所で待っていないと、まだ届いていないデータを使おうとして壊れる。

```javascript
// 危険: awaitを忘れると、Promise（まだ結果が来ていない箱）自体が返る
async function getUserName(userId) {
    const user = fetchUser(userId); // fetchUserがasync関数だとPromiseが返るだけ
    return user.name;               // user はPromiseなので .name は undefined になる
}

// 安全: awaitで「結果が届くまで待つ」ことを明示する
async function getUserName(userId) {
    const user = await fetchUser(userId);
    return user.name;
}
```

もう1つ典型的なのが、複数の非同期処理を「順番に」待つべきか「同時に」走らせていいかの判断ミスだ。

```javascript
// 遅い: 依存関係がないのに1つずつ順番に待っている（合計で待ち時間が積み上がる）
const user = await fetchUser(userId);
const orders = await fetchOrders(userId);

// 速い: 互いに依存しない処理なら同時に走らせ、両方揃うのを待つ
const [user, orders] = await Promise.all([fetchUser(userId), fetchOrders(userId)]);
```

逆に「Aの結果を使ってBを呼ぶ」ような依存関係がある処理を`Promise.all`で並列化してしまうと、Bがまだ存在しないAの結果を参照してエラーになる。「この2つの処理は互いの結果に依存しているか」を先に確認してから、順番に待つか同時に走らせるかを選ぶ。

## 2.4 エラー処理

想定外の事態が起きた時にどう振る舞うかの設計。`try`/`except`で例外を捕まえるのはいいが、`except: pass`のように**握りつぶす**と、エラーが起きたこと自体が誰にも見えなくなる。これが一番タチの悪いバグの隠し方。

握りつぶし以外にも、エラー処理には見落としやすい段階がある。

```python
# 悪い例1: 何が起きても同じように握りつぶす（何のエラーかすら分からない）
try:
    result = risky_operation()
except Exception:
    return None

# 悪い例2: 例外は捕まえているが、原因の手がかりを消して投げ直している
try:
    result = risky_operation()
except ValueError:
    raise RuntimeError("failed")  # 元の例外(ValueErrorの中身)が失われる

# 良い例: 想定される例外だけを狭く捕まえ、原因を保持したまま伝える
try:
    result = risky_operation()
except ValueError as e:
    raise RuntimeError(f"risky_operation failed: {e}") from e  # `from e`で元の例外を連鎖させる
```

「悪い例1」の`except Exception`は、`ValueError`のような想定内のエラーも、`KeyboardInterrupt`のようなプログラムを止めるべきシグナルも、コードのバグそのもの（`NameError`など）も、全部同じように握りつぶしてしまう。**捕まえる例外の型は、対処法を知っているものだけに絞る**のが原則。「悪い例2」は一見丁寧に見えるが、`raise ... from e`を使わずに例外を投げ直すと、スタックトレース（どこで最初に何が起きたかの記録）から元の例外の情報が失われ、ログを見ても本当の原因（今回なら`ValueError`が投げられた理由）が追えなくなる。

### 2.4.1 静的型付けと動的型付け

言語は大きく2つに分かれる。

- **静的型付け**（TypeScript、Java、Goなど）: 変数の型をコードを書いた時点（実行前）でチェックする。型のズレはコンパイルやビルドの段階でエラーになる
- **動的型付け**（Python、JavaScript、Rubyなど）: 型のチェックは実行時に行われる。2.2節の例のように、実行するまで型のズレに気づけないことがある

AIに書かせたコードが動的型付け言語の場合、「型が合っているか」は人間かテストが確認するしかない。型注釈（Pythonの`typing`、JavaScriptに対するTypeScript）を追加で導入すると、この確認の一部を機械（型チェッカー）に肩代わりさせられる。

## 2.5 ファイル・DB・ネットワーク

すべて「プログラムの外側」とやり取りする処理で、共通して次のリスクを持つ。

- 相手が存在しない・応答しない可能性がある(ファイルが消えている、DBが落ちている、通信が切れる)
- 処理に時間がかかる
- 途中で失敗した時、中途半端な状態が残る可能性がある

「外部とやり取りする箇所は必ず失敗しうる」という前提を持っておくと、AIに「エラー処理も入れて」と一言添えるだけで実装の質が変わる。

## 2.6 API

プログラム同士がやり取りするための取り決め。「何を送ると、何が返ってくるか」の契約。API呼び出しが失敗した時のステータスコード（400番台はリクエスト側のミス、500番台はサーバー側の問題、といった大枠)を知っておくと、AIへの状況説明が正確になる。

## 2.7 プロセス・スレッド

- **プロセス**: 独立して動くプログラムの実行単位。メモリ空間が分かれている
- **スレッド**: 1つのプロセスの中で並行して動く処理の単位。メモリを共有するため、同時に同じデータを書き換えると事故る（[5章の「同時実行」](05-breaking-it.md#51-壊し方の観点)に繋がる）

## 2.8 Git

- **commit**: 変更の区切り。「何をしたか」が一目で分かる粒度で切る
- **branch**: 本流（`main`）を汚さずに実験するための分岐
- **diff**: 変更前後の差分。AIに「このdiffの意図を説明して」と聞けるだけでレビューの質が上がる

「AIに直させて、ダメなら戻す」を安全に行えるかは、commitの粒度で決まる。

```
# 悪いcommitメッセージ: 「何を」しか書かれておらず、しかも粒度が大きすぎる
fix bug

# 良いcommitメッセージ: 「何を」「なぜ」が分かり、1つの変更に絞られている
支払い処理で残高チェック漏れによりマイナス残高になるバグを修正

process_payment() が balance の下限チェックをしていなかったため、
在庫と違い誰でも残高をマイナスにできる状態だった。壊し方は #5章 参照。
```

「fix bug」だけでは、後から`git log`を追った時にも、AIに「このcommitで何をしたか説明して」と聞いた時にも、diffを全部読まないと意味が分からない。1つのcommitに複数の無関係な変更（バグ修正とリファクタと機能追加）を混ぜてしまうと、後から「このバグ修正だけを取り消したい」と思っても他の変更まで巻き込んでしまう。**1コミット1目的**を守ると、AIに「この変更だけ元に戻して」と頼む時にも安全に切り戻せる。

## 演習

### 違和感探しクイズ

次のコードはAIが書きそうな「一見動くが危ういコード」の例だ。何が引っかかるか、2.1〜2.7の知識を使って指摘してみよう。

```python
def get_user_age(user_id):
    try:
        user = fetch_user_from_db(user_id)
        return user["age"]
    except:
        pass

def process_payment(amount):
    balance = get_balance()
    balance = balance - amount
    save_balance(balance)
    return "OK"
```

<details>
<summary>指摘のヒント（クリックして展開）</summary>

- `get_user_age`: `except: pass` でエラーを握りつぶしている（2.4）。ユーザーが存在しない・DB接続が切れているなど、失敗理由が一切分からず、戻り値も `None` になり呼び出し側が気づけない
- `get_user_age`: `user["age"]` が数値ではなく文字列で返ってくる可能性を検討していない（2.2）
- `process_payment`: `get_balance()` と `save_balance()` の間に他の処理が割り込むと、残高が二重に更新される可能性がある（同時実行、2.7）
- `process_payment`: 残高不足のチェックがない。マイナス残高になっても "OK" を返してしまう

</details>

### 実践課題

1. 直近でAIに書かせたコードを1つ選び、`try`/`except`（または相当するエラー処理構文）を全て探し出し、握りつぶしていないか確認する。
2. その中の1つの関数について、「入力（引数）」と「出力（戻り値）」を紙に書き出してから、実装を1行ずつ目で追う。

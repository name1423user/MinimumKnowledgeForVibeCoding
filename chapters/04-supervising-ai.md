## 4.1 良いプロンプトの作り方

曖昧な依頼は曖昧な実装しか生まない。

| 曖昧な言い方 | 精度の高い言い方 |
|---|---|
| 「なんかバグってる」 | 「〇〇を押すと△△というエラーが出る。再現手順は1,2,3」 |
| 「もっといい感じにして」 | 「この関数を、単一責任になるよう2つに分割して」 |
| 「セキュリティ大丈夫？」 | 「このフォームの入力値はエスケープせずにHTMLへ埋め込んでいないか確認して」 |
| 「重い」 | 「このループの中でDBクエリを毎回発行しているので、N+1になっていないか確認して」 |

### 曖昧なプロンプトが実際に何を引き起こすか

表を見ただけでは実感が湧きにくいので、1つのタスクで「曖昧な依頼」と「精度の高い依頼」がそれぞれ何を返すかを比較する。

> 依頼: 「ユーザー一覧をCSVでダウンロードできるようにして」

曖昧なまま投げると、AIは典型的な実装をハッピーケースで返す（[1.4節](01-ai-writes-code.md#14-aiがハッピーケースしか考えない理由)）。

```python
# 曖昧な依頼への典型的な回答: 件数・権限・文字コードのどれも考慮されていない
@app.route("/users/export")
def export_users():
    users = db.query("SELECT * FROM users")
    csv_data = to_csv(users)
    return csv_data
```

これを、次のように書き直す。

> 「ユーザー一覧をCSVでダウンロードできるようにして。ただし (1) admin権限のユーザーだけがアクセスできること (2) 10万件を超える可能性があるので一度に全件メモリに載せず分割して処理すること (3) 名前に日本語が含まれるのでExcelで開いた時に文字化けしないようUTF-8 BOM付きで出力すること」

```python
# 制約を明示した依頼への回答: 権限・データ量・文字コードの3点が反映される
@app.route("/users/export")
@require_role("admin")                       # (1) 権限チェック
def export_users():
    def generate():
        yield "﻿"                       # (3) UTF-8 BOMで文字化けを防ぐ
        for chunk in db.query_in_batches("SELECT * FROM users", batch_size=1000):  # (2) 分割処理
            yield to_csv(chunk)
    return Response(generate(), mimetype="text/csv")
```

違いを生んだのは「もっと良くして」という気合いではなく、**依頼文の中に具体的な制約を数字と条件で書いたこと**そのものだ。AIは指示されていない制約を推測で補ってはくれない。「権限」「データ量」「文字コード」のように、その機能で事故りやすいポイントを先に思いつく力は、本書のここまでの章（[第2章](02-reading-code.md)の型・外部入出力、[第3章](03-design.md)の設計、[第7章](07-security.md)のセキュリティ）で養う知識そのものになる。プロンプトが上手い人と下手な人の差は、言い回しのテクニックではなく「何を心配すべきか知っているかどうか」にある。

## 4.2 AIへのタスク分解

大きなタスクをそのまま渡すと、内部で矛盾した実装が混ざりやすい。「まずデータ構造を決める」「次にAPIのインターフェースを決める」「最後に実装する」のように、AI自身にも消化できる粒度に区切って渡す。

## 4.3 「実装して」ではなく「設計→実装→検証」

いきなり実装させず、まず「どう実装するつもりか」を言葉で説明させる。設計段階で違和感に気づけば、実装後の手戻りを防げる。実装後も「この実装で満たされていない仕様はないか」を検証させるところまでをワンセットにする。

## 4.4 AIにレビューさせる

自分が書いた（またはAIが書いた）コードを、別の観点から見直させる。「このコードのバグを3つ指摘して」のように、粗探しのモードを明示的に指定すると精度が上がる。

## 4.5 AI同士を対立させる

1つのAIの回答を鵜呑みにせず、別のAI（または同じAIに立場を変えさせて）に反論・検証させる。特に「本当にこれで合っているか」を疑わせるプロンプトは、見落としを拾い上げるのに有効。

## 4.6 AIの回答を鵜呑みにしない

AIは自信満々に間違えることがある（[1.5節](01-ai-writes-code.md#15-aiには限界がある)）。特に「存在しないはずの関数やライブラリを使っている」「バージョンが古い情報を前提にしている」ケースは、実際に動かして確認するまで信用しない。

### タスク分解の練習

「ユーザーがCSVファイルをアップロードして、商品データを一括登録できる機能」を、AIに渡す前に3〜4個のステップに分解してみる（4.2節・4.3節を参照）。「設計→実装→検証」のどの段階で何を確認するかも書き出すこと。

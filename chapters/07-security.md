セキュリティの話は個別に見ると膨大だが、根っこは1つだけ。

> **外部から来たデータは、形式・内容ともに一切信用しない。**

ユーザー入力、URLパラメータ、Cookie、他サイトのリソース、APIレスポンス——全部この「信頼境界」の外側にある。

## 7.1 入力値

保存・表示・実行する前に、必ず「そのデータは正しい形式か」を検証する。この検証（バリデーション）が抜けている箇所が、以下すべての脆弱性の入り口になる。

## 7.2 SQL Injection

「入力されたデータ」と「実行されるコード」の境界が曖昧になると起きる。

```python
# 危険: 文字列結合でSQLを組み立てる
query = f"SELECT * FROM users WHERE name = '{user_input}'"
# user_input が "' OR '1'='1" なら全件取得されてしまう

# 安全: プレースホルダを使う（パラメータ化クエリ）
cursor.execute("SELECT * FROM users WHERE name = ?", (user_input,))
```

なぜプレースホルダにするだけで安全になるのか、仕組みを理解しておく価値がある。文字列結合の場合、`user_input`の中身がそのままSQL文の**一部**として組み立てられるため、`' OR '1'='1`のような文字列を送ると、DBはそれを「データ」ではなく「クエリの構文の一部」として解釈してしまう。一方プレースホルダ（`?`や`%s`）を使うと、SQL文の**構造**とパラメータの**値**が分離した状態でDBドライバに渡される。DBは「これはWHERE句に渡す値そのものであり、構文としては解釈しない」と最初から扱うため、値の中に`'`や`OR`という文字列が含まれていても、それが構文として実行されることはない。「データ」と「命令」を混ぜて1本の文字列にすること自体が、SQL Injectionに限らずこの章で扱う脆弱性の共通の原因になる。

### 7.2.1 コマンドインジェクション

SQLと同じ構造の問題は、シェルコマンドを組み立てる時にも起きる。

```python
# 危険: ユーザー入力をそのままシェルコマンドに埋め込む
import os
os.system(f"ping -c 3 {host}")
# host が "example.com; rm -rf /" なら、pingの後に別のコマンドが実行されてしまう

# 安全: シェルを経由せず、引数を配列で渡す
import subprocess
subprocess.run(["ping", "-c", "3", host], shell=False)
```

`shell=True`（または`os.system`）を使うと、渡した文字列全体がシェルによって解釈されるため、`;`や`&&`、バッククォートのような**シェルにとって特別な意味を持つ文字**を使って、意図しない別のコマンドを継ぎ足される。配列で引数を渡す方式（`shell=False`）なら、`host`の中身はまるごと1つの引数として扱われ、シェルの構文として解釈されることがない。

### 7.2.2 パストラバーサル

ファイルパスの組み立てにも同じ罠がある。

```python
# 危険: ユーザーが指定したファイル名をそのままパスに使う
# <path:filename> はスラッシュを含む値も受け取れるコンバータ（既定の<filename>はスラッシュを含む値を弾いてしまう）
@app.route("/files/<path:filename>")
def get_file(filename):
    return open(f"/var/app/uploads/{filename}").read()
# filename が "../../etc/passwd" だと、意図しないファイルが読める

# 安全: ベースディレクトリの外に出ようとしていないか検証する
import os
@app.route("/files/<path:filename>")
def get_file(filename):
    base = os.path.realpath("/var/app/uploads")
    target = os.path.realpath(os.path.join(base, filename))
    if not target.startswith(base + os.sep):
        raise ValueError("invalid path")
    return open(target).read()
```

`../`（親ディレクトリへの移動）を含むファイル名を許してしまうと、アップロード用のディレクトリの外にある任意のファイルを読み書きされる。`os.path.realpath`で実際の絶対パスに正規化してから、意図したディレクトリの配下に収まっているかを確認するのが基本の対策になる。

### 7.2.3 SSRF（サーバーサイドリクエストフォージェリ）

「URLを指定させて、サーバー側からそのURLにアクセスする」機能（画像のURLを取り込む、Webhookの疎通確認など）にも、外部入力を信用しないという同じ原則が当てはまる。

```python
# 危険: ユーザーが指定した任意のURLにサーバーがアクセスしてしまう
@app.route("/fetch_thumbnail")
def fetch_thumbnail():
    url = request.args.get("url")
    return requests.get(url).content
# url に "http://169.254.169.254/latest/meta-data/" のような
# クラウド基盤の内部メタデータAPIを指定されると、サーバー自身に外部から到達できない
# 内部情報（認証情報など）を取得させられてしまう
```

ブラウザ経由の攻撃と違い、SSRFは**サーバー自身が持つ内部ネットワークへのアクセス権**を悪用される点が特徴で、外部からは直接アクセスできないはずの管理画面やクラウドのメタデータAPI、社内ネットワークの機器にリクエストを飛ばされる被害につながる。対策は、許可するURLのホスト名をホワイトリスト化する、プライベートIPアドレス帯（`127.0.0.1`、`169.254.0.0/16`、`10.0.0.0/8`など）へのアクセスを拒否する、といった形で「サーバーが到達できる範囲」自体を絞ることになる。

## 7.3 XSS（クロスサイトスクリプティング）

他人の入力をそのままHTMLとして表示すると、`<script>`タグごと実行されてしまう。テンプレートエンジンの自動エスケープを無効化するオプション(`| safe`など)を無意識に使うと穴になる。

## 7.4 CSRF（クロスサイトリクエストフォージェリ）

ログイン中のユーザーに、本人が気づかないうちにリクエストを送らせる攻撃。「ログイン状態＝そのユーザーの意図した操作」ではない、という前提が抜けると刺さる。ブラウザを作る場合は、あわせて**同一オリジンポリシー**（異なるドメイン間でのデータアクセスを制限する仕組み）も理解しておく必要がある。

### 7.4.1 安全でないデシリアライゼーション

**シリアライズ**は、プログラム内部のオブジェクトを保存・送信可能な形式（バイト列や文字列）に変換すること。**デシリアライゼーション**はその逆で、保存・受信したデータをプログラム内部のオブジェクトに復元することを指す。この復元処理を、信頼できない外部データに対して無防備に行うと危険な脆弱性になる。

```python
# 危険: 外部から受け取ったデータをpickleで復元する
import pickle
data = request.data  # 外部（ユーザー・他システム）から届いたバイト列
obj = pickle.loads(data)  # pickleは復元の過程で任意のコードを実行できてしまう

# 安全: 構造が固定されたJSONなど、コード実行の余地がない形式を使う
import json
obj = json.loads(request.data)
```

Pythonの`pickle`やRubyの`Marshal`のような一部のシリアライズ形式は、復元の過程で**任意のクラスのコンストラクタやメソッドを呼び出す**ことができる設計になっている。攻撃者が細工したデータを`pickle.loads`のような関数に渡せると、データを「復元」しているつもりが、実際には攻撃者が仕込んだコードを実行してしまう。JSONやYAMLの安全な読み込みモード（`yaml.safe_load`など）のように、**データの構造だけを表現しコードの実行を伴わない形式**を選ぶのが対策の基本になる。「信頼できないデータを復元する」という操作は、SQL・シェルコマンド・ファイルパスと並んで「データ」と「命令」の境界が壊れやすいポイントの1つだと覚えておく。

## 7.5 認証・認可

- **認証（Authentication）**: 「あなたは誰か」を確認する（ログイン）
- **認可（Authorization）**: 「あなたに何が許されているか」を確認する（権限）

ログインさえできれば全機能が使える設計は、認可の実装漏れであることが多い。

## 7.6 秘密情報

APIキー、秘密鍵、パスワードなどをコードに直書き（ハードコード）しない。環境変数や秘密管理サービスに置く。パスワードは平文はもちろん単純ハッシュ(MD5など)も危険で、`bcrypt`や`argon2`のような「ソルト付き・意図的に遅い」ハッシュ関数を使う。

## 7.7 権限分離

1つのプロセス・アカウントに必要以上の権限を与えない（最小権限の原則）。1箇所が乗っ取られた時の被害範囲を、権限を分けておくことで限定できる。

## 7.8 サンドボックス

信頼できないコードやデータを、システムの他の部分から隔離された環境で実行する仕組み。ブラウザがWebページのJavaScriptを実行する際の隔離も、この考え方の応用。

## 演習

### 脆弱性探しクイズ

次のコードには7.2〜7.6節で扱った問題が複数含まれている。何箇所指摘できるか試してみよう。

```python
API_KEY = "sk-live-abc123..."  # このファイルの先頭にベタ書き

@app.route("/search")
def search():
    keyword = request.args.get("q")
    query = f"SELECT * FROM products WHERE name LIKE '%{keyword}%'"
    results = db.execute(query)
    html = f"<p>「{keyword}」の検索結果</p>"
    return render(html, results)

@app.route("/admin/delete_user")
def delete_user():
    user_id = request.args.get("user_id")
    db.execute(f"DELETE FROM users WHERE id = {user_id}")
    return "deleted"

@app.route("/download")
def download():
    filename = request.args.get("name")
    return open(f"/var/app/reports/{filename}").read()
```

<details>
<summary>指摘のヒント（クリックして展開）</summary>

- `API_KEY` がコードに直書きされている（7.6）。環境変数に移すべき
- `search()`: `keyword` を文字列結合でSQLに埋め込んでいる（7.2、SQL Injection）
- `search()`: `keyword` をエスケープせずHTMLに埋め込んでいる（7.3、XSS）
- `delete_user()`: ログイン・権限チェックが一切なく、誰でもURLを叩けば任意のユーザーを削除できる（7.5、認証・認可の欠如）
- `delete_user()`: ここでも文字列結合でSQLを組み立てている（7.2）
- `download()`: `filename`に`../../etc/passwd`のような値を渡すと、意図したディレクトリの外のファイルを読める（7.2.2、パストラバーサル）

</details>

### 実践課題

1. 自分のアプリのコードから「外部入力（フォーム・URLパラメータ・APIレスポンスなど）をそのままSQL・HTML・シェルコマンド・ファイルパスに埋め込んでいる箇所」を検索して探す。1つも見つからなければ、なぜ安全と言えるかを説明できるか確認する。
2. `.env`や秘密情報管理の仕組みを使わずコードにハードコードされているキー・パスワードがないか、リポジトリ全体を`grep`で検索する。
3. 自分のアプリに「外部のURLを指定させて、サーバー側からそのURLへリクエストを送る」機能（画像取り込み、Webhook確認など）がないか確認する。あれば、指定できるURLの範囲（ホスト名、プライベートIPアドレスの拒否など）が制限されているか点検する（7.2.3、SSRF）。

# 第7章　セキュリティ

[← 目次に戻る](../README.md)

> **この章で学べること**
> - 「外部から来たデータは信用しない」という、セキュリティの唯一の根っこの原則
> - SQL Injection・XSS・CSRFなど代表的な脆弱性の成立条件と対策
> - 認証・認可の違い、秘密情報の扱い、最小権限の原則

セキュリティの話は個別に見ると膨大だが、根っこは1つだけ。

> **外部から来たデータは、形式・内容ともに一切信用しない。**

ユーザー入力、URLパラメータ、Cookie、他サイトのリソース、APIレスポンス——全部この「信頼境界」の外側にある。

## 7.1 入力値

保存・表示・実行する前に、必ず「そのデータは正しい形式か」を検証する。この検証（バリデーション）が抜けている箇所が、以下すべての脆弱性の入り口になる。

## 7.2 SQL Injection

「入力されたデータ」と「実行されるコード」の境界が曖昧になると起きる。

```python
# 危険: 文字列結合でSQLを組み立てる
query = f"SELECT * FROM users WHERE name = '{user_input}'"
# user_input が "' OR '1'='1" なら全件取得されてしまう

# 安全: プレースホルダを使う（パラメータ化クエリ）
cursor.execute("SELECT * FROM users WHERE name = ?", (user_input,))
```

## 7.3 XSS（クロスサイトスクリプティング）

他人の入力をそのままHTMLとして表示すると、`<script>`タグごと実行されてしまう。テンプレートエンジンの自動エスケープを無効化するオプション(`| safe`など)を無意識に使うと穴になる。

## 7.4 CSRF（クロスサイトリクエストフォージェリ）

ログイン中のユーザーに、本人が気づかないうちにリクエストを送らせる攻撃。「ログイン状態＝そのユーザーの意図した操作」ではない、という前提が抜けると刺さる。ブラウザを作る場合は、あわせて**同一オリジンポリシー**（異なるドメイン間でのデータアクセスを制限する仕組み）も理解しておく必要がある。

## 7.5 認証・認可

- **認証（Authentication）**: 「あなたは誰か」を確認する（ログイン）
- **認可（Authorization）**: 「あなたに何が許されているか」を確認する（権限）

ログインさえできれば全機能が使える設計は、認可の実装漏れであることが多い。

## 7.6 秘密情報

APIキー、秘密鍵、パスワードなどをコードに直書き（ハードコード）しない。環境変数や秘密管理サービスに置く。パスワードは平文はもちろん単純ハッシュ(MD5など)も危険で、`bcrypt`や`argon2`のような「ソルト付き・意図的に遅い」ハッシュ関数を使う。

## 7.7 権限分離

1つのプロセス・アカウントに必要以上の権限を与えない（最小権限の原則）。1箇所が乗っ取られた時の被害範囲を、権限を分けておくことで限定できる。

## 7.8 サンドボックス

信頼できないコードやデータを、システムの他の部分から隔離された環境で実行する仕組み。ブラウザがWebページのJavaScriptを実行する際の隔離も、この考え方の応用。

## 演習

### 脆弱性探しクイズ

次のコードには7.2〜7.6節で扱った問題が複数含まれている。何箇所指摘できるか試してみよう。

```python
API_KEY = "sk-live-abc123..."  # このファイルの先頭にベタ書き

@app.route("/search")
def search():
    keyword = request.args.get("q")
    query = f"SELECT * FROM products WHERE name LIKE '%{keyword}%'"
    results = db.execute(query)
    html = f"<p>「{keyword}」の検索結果</p>"
    return render(html, results)

@app.route("/admin/delete_user")
def delete_user():
    user_id = request.args.get("user_id")
    db.execute(f"DELETE FROM users WHERE id = {user_id}")
    return "deleted"
```

<details>
<summary>指摘のヒント（クリックして展開）</summary>

- `API_KEY` がコードに直書きされている（7.6）。環境変数に移すべき
- `search()`: `keyword` を文字列結合でSQLに埋め込んでいる（7.2、SQL Injection）
- `search()`: `keyword` をエスケープせずHTMLに埋め込んでいる（7.3、XSS）
- `delete_user()`: ログイン・権限チェックが一切なく、誰でもURLを叩けば任意のユーザーを削除できる（7.5、認証・認可の欠如）
- `delete_user()`: ここでも文字列結合でSQLを組み立てている（7.2）

</details>

### 実践課題

1. 自分のアプリのコードから「外部入力（フォーム・URLパラメータ・APIレスポンスなど）をそのままSQLやHTML、シェルコマンドに埋め込んでいる箇所」を検索して探す。1つも見つからなければ、なぜ安全と言えるかを説明できるか確認する。
2. `.env`や秘密情報管理の仕組みを使わずコードにハードコードされているキー・パスワードがないか、リポジトリ全体を`grep`で検索する。

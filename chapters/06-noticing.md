## 6.1 ログ設計

「何が」「いつ」「どういう状態で」起きたかを後から追えるように記録しておく。エラーだけでなく、「重要な操作が行われたこと」自体もログに残す価値がある。

```python
import logging

logger = logging.getLogger(__name__)

def process_payment(user_id, amount):
    logger.info("payment_started", extra={"user_id": user_id, "amount": amount})
    try:
        result = charge(user_id, amount)
        logger.info("payment_succeeded", extra={"user_id": user_id, "amount": amount})
        return result
    except ChargeError as e:
        # 握りつぶさず、状況が分かる情報とともに記録する（2.4節参照）
        logger.error("payment_failed", extra={"user_id": user_id, "amount": amount, "reason": str(e)})
        raise
```

## 6.2 エラー通知・監視

エラーが起きた瞬間に開発者が気づける仕組み（通知、監視ダッシュボードなど）。ログを残していても、誰も見ていなければ気づけないまま放置される。

## 6.3 「壊れたが誰も気づかなかった」を防ぐ

一番怖いのは、エラーになっていることにすら気づかず、ユーザーだけが被害を受け続ける状態。「エラーが起きたら必ず何らかの形で表面化する」ことを設計段階から意識する。

## 6.4 なぜ壊れたかを後から追える状態にする

エラーメッセージだけでなく、「その時どんな入力・状態だったか」が分かる情報を残しておくと、再現できない不具合の原因調査が格段に楽になる。

## 演習

1. 自分のアプリの中で、失敗した時に**何のログも残らない**箇所を1つ探す。6.1節の例を参考に、最低限「何が」「いつ」「どんな入力で」失敗したかが分かるログを追加する。
2. 「エラーが起きたが、ログにしか残らずユーザー・開発者の誰も気づかない」状態になっている処理がないか、自分のアプリを1つ点検する（6.3節）。
3. AIに「このエラー処理にログを追加して」と頼む時、6.1〜6.4節の観点（何を・いつ・どんな状態で残すか）を先に自分の言葉で指定してから依頼してみる。

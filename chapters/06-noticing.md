## 6.1 ログ設計

「何が」「いつ」「どういう状態で」起きたかを後から追えるように記録しておく。エラーだけでなく、「重要な操作が行われたこと」自体もログに残す価値がある。

```python
import logging

logger = logging.getLogger(__name__)

def process_payment(user_id, amount):
    logger.info("payment_started", extra={"user_id": user_id, "amount": amount})
    try:
        result = charge(user_id, amount)
        logger.info("payment_succeeded", extra={"user_id": user_id, "amount": amount})
        return result
    except ChargeError as e:
        # 握りつぶさず、状況が分かる情報とともに記録する（2.4節参照）
        logger.error("payment_failed", extra={"user_id": user_id, "amount": amount, "reason": str(e)})
        raise
```

### 6.1.1 ログレベルの使い分け

ログには重要度を表す「レベル」があり、正しく使い分けないとログ自体が形骸化する。

| レベル | 使う場面 | 悪い使い方の例 |
|---|---|---|
| DEBUG | 開発中の詳細な追跡情報 | 本番でDEBUGを出しっぱなしにして、量が多すぎて肝心なログが埋もれる |
| INFO | 正常な重要イベント（決済成功、ユーザー登録など） | ループの中で1件ごとにINFOを出し、大量発生でログ基盤のコストが爆発する |
| WARNING | 異常ではないが注意が必要な状態（リトライが発生した、非推奨機能を使ったなど） | 本来ERRORにすべき失敗をWARNINGで済ませ、誰も対応しない |
| ERROR | 処理が失敗し、対応が必要な状態 | エラーの詳細（入力値・原因）を書かず「エラーが発生しました」とだけ出す |
| CRITICAL | システム全体が継続困難な致命的な状態 | 復旧可能な一時的エラーまでCRITICALにして、本当の緊急事態が埋もれる |

ログレベルの使い分けを誤ると2種類の失敗が起きる。1つは「全部INFOかERRORで出す」ことで重要度の区別がつかなくなること。もう1つは、[2.4節](02-reading-code.md#24-エラー処理)で触れた**秘密情報のログ出力**だ。デバッグのためにパスワードやAPIキー、クレジットカード番号をログに含めてしまうと、ログ基盤自体が漏洩リスクの塊になる。「このログに何を含めるか」は、[7.6節「秘密情報」](07-security.md#76-秘密情報)の観点とセットで考える。

## 6.2 エラー通知・監視

エラーが起きた瞬間に開発者が気づける仕組み（通知、監視ダッシュボードなど）。ログを残していても、誰も見ていなければ気づけないまま放置される。

## 6.3 「壊れたが誰も気づかなかった」を防ぐ

一番怖いのは、エラーになっていることにすら気づかず、ユーザーだけが被害を受け続ける状態。「エラーが起きたら必ず何らかの形で表面化する」ことを設計段階から意識する。

## 6.4 なぜ壊れたかを後から追える状態にする

エラーメッセージだけでなく、「その時どんな入力・状態だったか」が分かる情報を残しておくと、再現できない不具合の原因調査が格段に楽になる。

## 6.5 観測可能性（オブザーバビリティ）の3本柱

「気づく仕組み」を体系立てて考える時、ログだけでなく次の3種類を組み合わせるのが一般的だ。

- **ログ（Logs）**: 「いつ・何が・どんな状態で」起きたかの個別記録。6.1節で扱った内容
- **メトリクス（Metrics）**: 「エラー率」「レスポンスタイム」「秒間リクエスト数」のような、時系列で集計された数値。個別の事象ではなく「全体の傾向」を見る。例えば「エラー率が急に5%を超えたらアラートを出す」といった閾値の監視はメトリクスの役割
- **トレース（Traces）**: 1つのリクエストが複数のサービス・関数をまたいで処理される時、「どこで時間がかかったか」「どこで失敗したか」を1本の線として追跡する記録。マイクロサービス構成や、外部APIを何段も呼ぶ処理で特に威力を発揮する

ログだけでは「今システム全体が健康かどうか」を一目で判断できず、メトリクスだけでは「なぜそのエラーが起きたか」の詳細が分からない。小規模なアプリではログだけで十分なことも多いが、「エラー率が上がった原因を、ログを1件ずつ漁って探している」状態になってきたら、メトリクスやトレースの導入を検討する段階だと考えていい。

## 演習

1. 自分のアプリの中で、失敗した時に**何のログも残らない**箇所を1つ探す。6.1節の例を参考に、最低限「何が」「いつ」「どんな入力で」失敗したかが分かるログを追加する。
2. 「エラーが起きたが、ログにしか残らずユーザー・開発者の誰も気づかない」状態になっている処理がないか、自分のアプリを1つ点検する（6.3節）。
3. AIに「このエラー処理にログを追加して」と頼む時、6.1〜6.4節の観点（何を・いつ・どんな状態で残すか）を先に自分の言葉で指定してから依頼してみる。

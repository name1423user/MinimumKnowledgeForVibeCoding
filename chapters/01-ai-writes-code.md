## 1.1 バイブコーディングとは何か

厳密な仕様や設計を書かず、AIとの対話を通じて「動くもの」を素早く作っていく開発スタイル。速度は圧倒的に上がるが、代償として「なぜ動いているか」への理解が薄くなりやすい。この本はその代償を最小化するために存在する。

## 1.2 AIに任せていい仕事・ダメな仕事

| 任せていい | 任せると危険 |
|---|---|
| 定型的なコードの雛形生成 | セキュリティに関わる判断（認証方式の選定など） |
| 単純作業の自動化（リファクタ、命名の統一） | 「なぜこの設計にしたか」の意思決定そのもの |
| エラーメッセージの解読補助 | 検証していない外部データの扱い方の最終判断 |
| テストケースの列挙 | 本番データを操作する破壊的な処理の実行 |

判断基準はシンプルで、「間違っていた場合に気づけるか」。自分が結果を検証できない仕事をAIに丸投げするのが一番危ない。

## 1.3 「動く」と「正しい」は違う

「動く」は「今、目の前のケースでエラーが出ていない」という意味でしかない。「正しい」は「意図した仕様を、想定される全てのケースで満たしている」という意味だ。バイブコーディングは前者で満足しがちで、後者の検証を飛ばす。[第5章「壊す」](05-breaking-it.md)がこのギャップを埋めるための章になる。

このギャップは抽象論より、実際のコードで見たほうが早い。「在庫を1つ減らす」という一見単純な処理を例にする。

```python
# 「動く」実装: デモで見せれば普通に動く。レビューでも一見素通りしやすい
def decrement_stock(product_id, quantity):
    stock = get_stock(product_id)
    stock.count = stock.count - quantity
    save_stock(stock)
    return {"ok": True}

# 「正しい」実装: 仕様として明示されないと出てこない分岐が増える
def decrement_stock(product_id, quantity):
    if quantity <= 0:
        raise ValueError("quantity must be positive")  # 0や負数の注文を弾く
    stock = get_stock(product_id)
    if stock is None:
        raise LookupError(f"product {product_id} not found")  # 存在しない商品IDへの対処
    if stock.count < quantity:
        raise InsufficientStockError(stock.count, quantity)  # 在庫不足を「動いたつもり」で通さない
    with db.transaction():  # 他の注文が同時に同じ在庫を減らしても壊れないようにする（5章「同時実行」）
        stock.count -= quantity
        save_stock(stock)
    return {"ok": True, "remaining": stock.count}
```

上の「動く」版は、`quantity=1`・在庫が十分にあるという**典型的な1ケース**でしか検証されていない。負の数量、存在しない商品ID、在庫不足、同時アクセスの4つは、機能としては「仕様の一部」であるにもかかわらず、コードのどこにも存在しない。これらはテストを書いて初めて欠落に気づけることが多く、[第5章](05-breaking-it.md)で扱う「壊し方」はまさにこの4つのような欠落を機械的に洗い出す手順にあたる。

## 1.4 AIがハッピーケースしか考えない理由

AIは、指示された内容を最も自然に満たす「典型的な」実装を出力するよう学習されている。典型的な実装は、典型的な入力（正しい形式・妥当な範囲の値）を前提にしていることが多い。「空文字列が来たら」「途中でネットワークが切れたら」といった非典型ケースは、明示的に頼まない限り出てこないと考えたほうがいい。

この背景にはもう少し具体的な理由がある。

- **学習データの偏り**: AIの学習元には、チュートリアルやドキュメントの例、GitHub上の「動作説明用」コードが大量に含まれる。こうしたコードは説明を短く保つために意図的にエラー処理を省いていることが多く、AIは「これが典型的な書き方だ」という分布を学習してしまう
- **短く自然な回答が高く評価されやすい**: 学習の過程で、簡潔で読みやすい回答が好まれるように調整されている。防御的なコード（バリデーション、例外処理、ロールバック）は行数が増えて「野暮ったく」見えるため、明示的に求めない限り省略される方向に倒れやすい
- **「仕様」と「例」を区別できない**: 「在庫を減らす関数を書いて」という依頼は、AIにとって「典型的な在庫減算のコード例を出す」タスクに見える。それが「本番で使う仕様」なのか「概念を説明するための例」なのかは、こちらが明示しない限り区別されない

対策は単純で、上のコード例のように「境界値」「異常系」「同時実行」を依頼文に**名指しで**含めることだ。「エラー処理も入れて」のような一般的な指示より、「在庫が足りない場合と、同じ商品を同時に注文された場合の扱いを含めて」のように具体的な状況を列挙したほうが、AIの出力は実際の仕様に近づく。

## 1.5 AIには「限界」がある

- **コンテキストを忘れる**: 会話が長くなるほど、序盤に決めた前提や制約を守らなくなる。重要な制約は都度思い出させる必要がある
- **大きすぎるタスクは破綻する**: 「アプリ全部作って」のような粒度では、内部で矛盾した実装が混ざりやすい。[第4章の「タスク分解」](04-supervising-ai.md#42-aiへのタスク分解)がこの対策になる
- **自信満々に間違える**: 分からないことを「分からない」と言わず、もっともらしい嘘（ハルシネーション）を出すことがある。特に存在しないライブラリ関数やAPIをでっち上げるケースに注意

  ```python
  # AIが自信を持って提示してくるが、実際には存在しないメソッド名の例
  df.groupby("category").sort_values("count")  # DataFrameGroupByにsort_valuesは存在しない
  # 正しくは、集計してからDataFrameに戻した上でsort_valuesを呼ぶ
  df.groupby("category").size().reset_index(name="count").sort_values("count")
  ```

  こうしたハルシネーションが起きるのは、AIが「関数が実在するかどうかを事前に調べてから答える」仕組みではなく、「学習データの中でその文脈に**最も自然に続きそうな単語列**」を予測して出力しているためだ。`groupby`の後に`sort_values`のような名前が続く例が学習データに数多くあれば、実際にそのメソッドが存在しなくても、もっともらしい並びとして出力されうる。加えてライブラリのバージョンによってAPIが変わる（あるバージョンで存在した関数が次のバージョンで削除される）ため、学習時点のバージョンと手元の環境のバージョンがずれているだけでも、同じ現象が起きる。対策は「実際に実行して確認する」以外になく、公式ドキュメントやIDEの補完でメソッドの実在を裏取りする習慣が必要になる

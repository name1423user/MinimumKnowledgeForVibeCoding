# # AIとコードを書くための教科書
### バイブコーディングに最低限必要な知識

---

## はじめに

バイブコーディングの本当の問題点は、「コードが書けないこと」ではない。**自分が今何をしていて、何が起きているかを言語化できないこと**だ。

AIは万能翻訳機ではない。頭の中の「なんかこう、いい感じにしたい」を正確なコードに変換する装置ではなく、**与えた言葉の精度でしか働かない**装置だ。この本は、その言葉の精度を上げるための最短ルートを示す。

各章は次の流れで進む。

> 知識 → AIに実装させる → AIの出力を疑う → 壊す → なぜ壊れたか理解する

全部を一度に暗記する必要はない。「この概念の存在を知っていて、必要になったら深掘りできる」状態がゴールだ。

---

## 第1章　AIにコードを書かせる

### 1.1 バイブコーディングとは何か

厳密な仕様や設計を書かず、AIとの対話を通じて「動くもの」を素早く作っていく開発スタイル。速度は圧倒的に上がるが、代償として「なぜ動いているか」への理解が薄くなりやすい。この本はその代償を最小化するために存在する。

### 1.2 AIに任せていい仕事・ダメな仕事

| 任せていい | 任せると危険 |
|---|---|
| 定型的なコードの雛形生成 | セキュリティに関わる判断（認証方式の選定など） |
| 単純作業の自動化（リファクタ、命名の統一） | 「なぜこの設計にしたか」の意思決定そのもの |
| エラーメッセージの解読補助 | 検証していない外部データの扱い方の最終判断 |
| テストケースの列挙 | 本番データを操作する破壊的な処理の実行 |

判断基準はシンプルで、「間違っていた場合に気づけるか」。自分が結果を検証できない仕事をAIに丸投げするのが一番危ない。

### 1.3 「動く」と「正しい」は違う

「動く」は「今、目の前のケースでエラーが出ていない」という意味でしかない。「正しい」は「意図した仕様を、想定される全てのケースで満たしている」という意味だ。バイブコーディングは前者で満足しがちで、後者の検証を飛ばす。第5章「壊す」がこのギャップを埋めるための章になる。

### 1.4 AIがハッピーケースしか考えない理由

AIは、指示された内容を最も自然に満たす「典型的な」実装を出力するよう学習されている。典型的な実装は、典型的な入力（正しい形式・妥当な範囲の値）を前提にしていることが多い。「空文字列が来たら」「途中でネットワークが切れたら」といった非典型ケースは、明示的に頼まない限り出てこないと考えたほうがいい。

### 1.5 AIには「限界」がある

- **コンテキストを忘れる**: 会話が長くなるほど、序盤に決めた前提や制約を守らなくなる。重要な制約は都度思い出させる必要がある
- **大きすぎるタスクは破綻する**: 「アプリ全部作って」のような粒度では、内部で矛盾した実装が混ざりやすい。第4章の「タスク分解」がこの対策になる
- **自信満々に間違える**: 分からないことを「分からない」と言わず、もっともらしい嘘（ハルシネーション）を出すことがある。特に存在しないライブラリ関数やAPIをでっち上げるケースに注意

## 第2章　コードを読むための最低限の知識

書けなくていい。ただし、AIが出したコードを読んで**違和感に気づける**ことが最重要スキルだ。

### 2.1 変数・関数・クラス

- **変数**: 値に名前をつけて保管する箱。「今どんな値が入っているか」を追えることが読解の基本
- **関数**: 処理のまとまりに名前をつけたもの。入力（引数）と出力（戻り値）の対応を意識する
- **クラス**: データとそれを操作する処理をひとまとめにした設計図。「このクラスは何を管理しているオブジェクトか」を一言で言えるかが理解の指標

### 2.2 型

値の種類（数値・文字列・真偽値・リストなど）。型が合わないと計算やAPIとのやり取りで想定外の挙動になる。「この変数は文字列のはずが数値だった」のようなズレが、バイブコーディングで頻発するバグの典型。

### 2.3 非同期処理

「今すぐ終わらない処理（通信、ファイル読み込みなど）」を、待っている間も他の処理を進められるようにする仕組み。`async`/`await`のような構文を見たら、「この処理は即座には終わらない」と意識する。待つべき箇所で待っていないと、まだ届いていないデータを使おうとして壊れる。

### 2.4 エラー処理

想定外の事態が起きた時にどう振る舞うかの設計。`try`/`except`で例外を捕まえるのはいいが、`except: pass`のように**握りつぶす**と、エラーが起きたこと自体が誰にも見えなくなる。これが一番タチの悪いバグの隠し方。

### 2.5 ファイル・DB・ネットワーク

すべて「プログラムの外側」とやり取りする処理で、共通して次のリスクを持つ。

- 相手が存在しない・応答しない可能性がある(ファイルが消えている、DBが落ちている、通信が切れる)
- 処理に時間がかかる
- 途中で失敗した時、中途半端な状態が残る可能性がある

「外部とやり取りする箇所は必ず失敗しうる」という前提を持っておくと、AIに「エラー処理も入れて」と一言添えるだけで実装の質が変わる。

### 2.6 API

プログラム同士がやり取りするための取り決め。「何を送ると、何が返ってくるか」の契約。API呼び出しが失敗した時のステータスコード（400番台はリクエスト側のミス、500番台はサーバー側の問題、といった大枠)を知っておくと、AIへの状況説明が正確になる。

### 2.7 プロセス・スレッド

- **プロセス**: 独立して動くプログラムの実行単位。メモリ空間が分かれている
- **スレッド**: 1つのプロセスの中で並行して動く処理の単位。メモリを共有するため、同時に同じデータを書き換えると事故る（後述の「同時実行」に繋がる）

### 2.8 Git

- **commit**: 変更の区切り。「何をしたか」が一目で分かる粒度で切る
- **branch**: 本流（`main`）を汚さずに実験するための分岐
- **diff**: 変更前後の差分。AIに「このdiffの意図を説明して」と聞けるだけでレビューの質が上がる

「AIに直させて、ダメなら戻す」を安全に行えるかは、commitの粒度で決まる。

## 第3章　設計する

### 3.1 要件と仕様

**要件**は「何を実現したいか」、**仕様**は「それをどう振る舞いとして定義するか」。「ログイン機能が欲しい」は要件、「メールとパスワードで認証し、5回失敗したらロックする」は仕様。AIに実装を頼む前に、この2つを分けて言葉にできているかを確認する。

### 3.2 抽象化

細かい実装の違いを覆い隠し、「共通して大事な部分だけ」を扱えるようにすること。「支払い方法がクレジットカードか銀行振込かは知らなくても、`pay()`さえ呼べば支払いが完了する」状態を作るのが抽象化。

### 3.3 インターフェース

「これだけ渡せば、これが返ってくる」という外部との約束事。中身の実装を差し替えても、インターフェースが変わらなければ呼び出し側は影響を受けない。

### 3.4 責務分離

「1つの部品は1つのことだけをする」という原則。目安は「その部品の説明に『それと』が出てきたら分割サイン」。

- 悪い例: 「ユーザーを検証**して**、DBに保存**して**、メールを送る関数」
- 良い例: `validate_user()` / `save_user()` / `send_welcome_email()`

### 3.5 依存関係

AがBを使っている時、「AはBに依存している」という。依存が多い・深いほど、Bを直した時にAが壊れるリスクが増える。「AはBの入り口（インターフェース）だけを知っていればいい」状態を目指すのが疎結合の考え方。

### 3.6 状態管理

「値が変化しうるデータ（状態）」をどこに置くかで設計の質が決まる。グローバルな場所に置くとどこからでも書き換えられて追跡不能になりやすい。必要な範囲（関数・クラス・コンポーネント）に閉じ込めるほど、影響範囲が予測できる。

### 3.7 データ設計

どんなデータを、どんな形（テーブル・構造）で持つか。後から変更しづらい部分なので、「このデータは将来どう増えうるか」を最初に考えておく価値が高い。正規化（重複を排除する設計）と非正規化（速度のためにあえて重複を許す設計）のトレードオフも知っておく。

### 3.8 アーキテクチャ

システム全体をどんな部品に分け、どう繋ぐかという大枠の設計。「フロントエンドとバックエンドを分ける」「機能ごとにモジュールを分ける」といった判断がここに含まれる。最初から完璧を目指さず、「今後どこが変わりそうか」を予測して、そこだけ差し替えやすくしておくのが現実的。

### 3.9 パフォーマンス設計

「動く」の中には「速く動く」も含まれる。

- **計算量（O記法）**: データが増えた時、処理時間がどう増えるか。for文の中でfor文を回す（O(n²)）は、データ量が増えると急激に重くなる典型パターン
- **N+1問題**: 1件ずつDBに問い合わせるループを書いてしまい、本来1回で済む処理をN回実行してしまうバグ
- **キャッシュ**: 一度計算・取得した結果を保存し、再利用する。「いつ古くなるか（無効化のタイミング）」の設計が一番難しい

## 第4章　AIを監督する

### 4.1 良いプロンプトの作り方

曖昧な依頼は曖昧な実装しか生まない。

| 曖昧な言い方 | 精度の高い言い方 |
|---|---|
| 「なんかバグってる」 | 「〇〇を押すと△△というエラーが出る。再現手順は1,2,3」 |
| 「もっといい感じにして」 | 「この関数を、単一責任になるよう2つに分割して」 |
| 「セキュリティ大丈夫？」 | 「このフォームの入力値はエスケープせずにHTMLへ埋め込んでいないか確認して」 |
| 「重い」 | 「このループの中でDBクエリを毎回発行しているので、N+1になっていないか確認して」 |

### 4.2 AIへのタスク分解

大きなタスクをそのまま渡すと、内部で矛盾した実装が混ざりやすい。「まずデータ構造を決める」「次にAPIのインターフェースを決める」「最後に実装する」のように、AI自身にも消化できる粒度に区切って渡す。

### 4.3 「実装して」ではなく「設計→実装→検証」

いきなり実装させず、まず「どう実装するつもりか」を言葉で説明させる。設計段階で違和感に気づけば、実装後の手戻りを防げる。実装後も「この実装で満たされていない仕様はないか」を検証させるところまでをワンセットにする。

### 4.4 AIにレビューさせる

自分が書いた（またはAIが書いた）コードを、別の観点から見直させる。「このコードのバグを3つ指摘して」のように、粗探しのモードを明示的に指定すると精度が上がる。

### 4.5 AI同士を対立させる

1つのAIの回答を鵜呑みにせず、別のAI（または同じAIに立場を変えさせて）に反論・検証させる。特に「本当にこれで合っているか」を疑わせるプロンプトは、見落としを拾い上げるのに有効。

### 4.6 AIの回答を鵜呑みにしない

AIは自信満々に間違えることがある（1.5節）。特に「存在しないはずの関数やライブラリを使っている」「バージョンが古い情報を前提にしている」ケースは、実際に動かして確認するまで信用しない。

## 第5章　壊す

「動く」を確認しただけでは「正しい」とは言えない（1.3節）。この章では、意図的にコードを壊しにいく。

- **境界値**: 0、負数、最大値、配列の最初と最後など、ちょうど切り替わる地点
- **異常系**: 想定していない種類の入力（数値のはずが文字列、必須項目が欠けているなど）
- **空データ**: リストが空、文字列が空、そもそもデータが存在しない
- **巨大データ**: 想定より桁違いに大きい入力やファイル
- **同時実行**: 複数のリクエストが同時に同じデータを書き換えようとする
- **ネットワーク切断**: 通信の途中で相手が応答しなくなる
- **権限不足**: 本来アクセスできないはずのユーザーがアクセスを試みる
- **データ破損**: 保存されているデータの形式が壊れている
- **再起動**: アプリやサーバーが処理の途中で再起動する
- **二重実行**: 同じ処理（決済など）が誤って2回実行される

### 5.11 壊し方をテストコードに変換する

手で壊して見つけたバグは、そのまま忘れると同じバグが後で復活する。見つけた壊し方を**テストコード**として残すことで、「二度と同じ理由では壊れない」状態を保証できる。

- **単体テスト**: 1つの関数・機能だけを狭く検証する
- **結合テスト**: 複数の部品を組み合わせた時の動作を検証する

テストの本当の目的は「バグを見つけること」より、「後で仕様を変えた時、壊れたことに気づけること」にある。

## 第6章　気づく

意図的に壊す第5章とは対になる、「本番で勝手に壊れた時にどう気づくか」の章。

### 6.1 ログ設計

「何が」「いつ」「どういう状態で」起きたかを後から追えるように記録しておく。エラーだけでなく、「重要な操作が行われたこと」自体もログに残す価値がある。

### 6.2 エラー通知・監視

エラーが起きた瞬間に開発者が気づける仕組み（通知、監視ダッシュボードなど）。ログを残していても、誰も見ていなければ気づけないまま放置される。

### 6.3 「壊れたが誰も気づかなかった」を防ぐ

一番怖いのは、エラーになっていることにすら気づかず、ユーザーだけが被害を受け続ける状態。「エラーが起きたら必ず何らかの形で表面化する」ことを設計段階から意識する。

### 6.4 なぜ壊れたかを後から追える状態にする

エラーメッセージだけでなく、「その時どんな入力・状態だったか」が分かる情報を残しておくと、再現できない不具合の原因調査が格段に楽になる。

## 第7章　セキュリティ

セキュリティの話は個別に見ると膨大だが、根っこは1つだけ。

> **外部から来たデータは、形式・内容ともに一切信用しない。**

ユーザー入力、URLパラメータ、Cookie、他サイトのリソース、APIレスポンス——全部この「信頼境界」の外側にある。

### 7.1 入力値

保存・表示・実行する前に、必ず「そのデータは正しい形式か」を検証する。この検証（バリデーション）が抜けている箇所が、以下すべての脆弱性の入り口になる。

### 7.2 SQL Injection

「入力されたデータ」と「実行されるコード」の境界が曖昧になると起きる。

```python
# 危険: 文字列結合でSQLを組み立てる
query = f"SELECT * FROM users WHERE name = '{user_input}'"
# user_input が "' OR '1'='1" なら全件取得されてしまう

# 安全: プレースホルダを使う（パラメータ化クエリ）
cursor.execute("SELECT * FROM users WHERE name = ?", (user_input,))
```

### 7.3 XSS（クロスサイトスクリプティング）

他人の入力をそのままHTMLとして表示すると、`<script>`タグごと実行されてしまう。テンプレートエンジンの自動エスケープを無効化するオプション(`| safe`など)を無意識に使うと穴になる。

### 7.4 CSRF（クロスサイトリクエストフォージェリ）

ログイン中のユーザーに、本人が気づかないうちにリクエストを送らせる攻撃。「ログイン状態＝そのユーザーの意図した操作」ではない、という前提が抜けると刺さる。ブラウザを作る場合は、あわせて**同一オリジンポリシー**（異なるドメイン間でのデータアクセスを制限する仕組み）も理解しておく必要がある。

### 7.5 認証・認可

- **認証（Authentication）**: 「あなたは誰か」を確認する（ログイン）
- **認可（Authorization）**: 「あなたに何が許されているか」を確認する（権限）

ログインさえできれば全機能が使える設計は、認可の実装漏れであることが多い。

### 7.6 秘密情報

APIキー、秘密鍵、パスワードなどをコードに直書き（ハードコード）しない。環境変数や秘密管理サービスに置く。パスワードは平文はもちろん単純ハッシュ(MD5など)も危険で、`bcrypt`や`argon2`のような「ソルト付き・意図的に遅い」ハッシュ関数を使う。

### 7.7 権限分離

1つのプロセス・アカウントに必要以上の権限を与えない（最小権限の原則）。1箇所が乗っ取られた時の被害範囲を、権限を分けておくことで限定できる。

### 7.8 サンドボックス

信頼できないコードやデータを、システムの他の部分から隔離された環境で実行する仕組み。ブラウザがWebページのJavaScriptを実行する際の隔離も、この考え方の応用。

## 第8章　実践

知識を頭に入れただけでは身につかない。小さなアプリを題材に、一連の流れを実際に回す。

1. **AIに小さなアプリを作らせる** — 仕様はあえて簡潔に伝える
2. **わざと仕様漏れを入れる** — 「空欄のまま送信したら」のようなケースを最初は伝えない
3. **AIに実装させる** — ハッピーケースだけの実装が出てくることを確認する
4. **自分でレビューする** — 第2〜3章の知識を使って、違和感に気づけるか試す
5. **壊してみる** — 第5章の観点で、実際に境界値・異常系を試す
6. **修正する** — 見つかった問題をAIに直させる。この時、精度の高い指示(第4章)が効いてくる
7. **壊し方をテスト化する** — 見つけたバグをテストコードとして残す(5.11節)
8. **気づく仕組みを入れる** — ログや通知を仕込み、次に壊れた時に自分で気づけるようにする(第6章)
9. **最後に設計を改善する** — 一通り動いた後で、責務分離やデータ設計(第3章)に無理がないか見直す

このループを一度でも自分の手で回せれば、以降のバイブコーディングの質が確実に変わる。

## 付録　あれば便利な知識

必須ではないが、知っていると詰まる回数が減る知識。

- **環境構築の基礎**（仮想環境/venv、Docker超入門、環境変数の扱い）— 「自分のPCでは動くのに他の環境で動かない」の9割はここが原因
- **CLIツールに慣れる**（`grep`, `curl`, `jq`など）— AIが出したコマンドの意味を理解して、コピペで終わらせない
- **正規表現の基礎** — 読めないと「なんかこのパターンにマッチしない」で詰まる
- **設定ファイルのフォーマット**（JSON/YAML/TOML）— 読み書きに慣れておくと、AIとの設定周りのやり取りが速くなる
- **ドキュメントの読み方** — 公式ドキュメント優先。Stack Overflowや古い記事の情報が今も正しいとは限らない
- **セマンティックバージョニング**（`1.2.3`の意味）— ライブラリ更新で急に壊れる理由が分かる
- **ライセンスの基礎** — 依存ライブラリのライセンス(MIT/GPLなど)を無視すると公開時に事故る
- **README/コミットメッセージの書き方** — 未来の自分とAIへの引き継ぎ資料になる
- **ローカルと本番の違い** — OS差、パスの違い、環境変数の有無で「なぜかここだけ動かない」が起きる
- **複数のAIツールの使い分け** — クラウドAPI系とローカルLLM、それぞれの得意不得意を知っておくとタスクの振り分けが上手くなる
- **エディタ/ターミナルの効率化** — ショートカットや補完に慣れるだけで、AIとの往復回数自体が減る

## おわりに

この本に書かれた概念は、全部「言葉を知っていること」が第一歩になっている。バイブコーディングが危険なのは、AIに頼ること自体ではなく、**AIが出したものを評価する言葉を自分が持たないまま採用してしまうこと**だ。

一度に全部理解しようとしなくていい。手を動かしていて「あ、これさっき読んだやつだ」と思い出せたら、その章はもう自分のものになっている。
